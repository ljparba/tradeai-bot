# TradeAI HELD_OUT_DAYS — Plain-Language Explainer + Honest Audit

> **Purpose.** A non-programmer's reference for what `HELD_OUT_DAYS` actually does in TradeAI. Generated by a **read-only audit** on 2026-05-31 — 4 parallel specialist agents traced the variable through `backtest.py`, `walk_forward.py`, `validation.py`, `adaptive_engine.py`, `scripts/autonomous_explorer.py`, and `scripts/compute_cross_config_sr_std.py`. Nothing was modified.
>
> **The headline.** HELD_OUT_DAYS is a **signal lockbox**, NOT a **data lockbox**. The name oversells what the code actually delivers. Use it correctly and it provides a useful sanity check. Use it expecting "the strategy has never seen the most recent 90 days" and you will get an answer that is at least partially false.

---

## 1. WHAT IT DOES — When you set HELD_OUT_DAYS=90, what actually happens?

### Plain language

The strategy **still sees** the most recent 90 days of price data when generating signals, computing indicators (EMA, ATR, ADX, regime, swings, FVGs), evaluating gates, and computing TP/SL placement. **It is not a data lockbox.**

What actually happens, step by step:

1. `backtest.py:253` reads `HELD_OUT_DAYS` from the environment (default `0` = disabled).
2. `backtest.py:4112-4116` fetches the **FULL 365 days** of OHLCV (4H, 1H, 5M candles) for every token. **No data is hidden here.**
3. `backtest.py:4132-4148` (5M_SWEEP scanner) and `backtest.py:4158-4167` (CRT scanner) simulate signals over the **ENTIRE 365-day candle history**. Every indicator, every gate (4H bias, 1H trend, MSS, FVG, sweep detection), every ATR/SL/TP calculation runs over the most-recent 90 days **exactly as it does over the rest of the year**.
4. **ONLY AFTER** all signals are generated, `backtest.py:4196-4204` calls `walk_forward.split_held_out(all_signals, ...)`.
5. `walk_forward.py:245-296` takes the **list of already-generated signal dictionaries** and partitions them by their `ts` field (signal timestamp). Older signals → `_tune_sigs`; newer signals (within `HELD_OUT_DAYS` of wall-clock now) → `_held_sigs`.
6. The primary CPCV cross-validation (`backtest.py:4305`), the 12-window walk-forward report (`backtest.py:4421`), and the print report (`backtest.py:4212-4213`) all then consume `_tune_sigs` only — tuning portion only.
7. The held-out portion gets exactly **one** scoring pass at `backtest.py:4428` via `held_out_summary` (no CPCV folds), which prints a one-shot WR + Wilson confidence interval + gap-vs-tuning verdict.

### What you've actually bought with HELD_OUT_DAYS=90

✅ The CPCV combinatorial folds no longer include signals from the most-recent 90 days.
✅ You get a separate, one-shot WR number for the held-out portion to compare against tuning-portion WR.
✅ The `[PHASE C GATE]` printed line gives you a quick sanity check: did the strategy's WR on the most-recent 90 days roughly match its WR on the older 275 days?

### What you have NOT bought

❌ The strategy DID see all 365 days when generating signals.
❌ The OHLCV cache key is unchanged regardless of HELD_OUT_DAYS (`backtest.py:411`) — the same cached 365-day file is reused.
❌ A "clean held-out window the strategy has never touched" — that does **not** exist in the current code.

**Source files audited:** `backtest.py:253, 411, 4112-4116, 4132-4148, 4158-4167, 4193-4213, 4305, 4421, 4424-4440, 4461`; `walk_forward.py:245-297`.

## 2. IS IT CORRECTLY IMPLEMENTED — Honest leakage hunt

The leakage agent audited 7 paths through which held-out data could still influence the tuning result. The breakdown is mixed — some paths are clean by careful design, others leak.

### ✅ Paths that respect the boundary

| Path | Why it's clean | File:line |
|---|---|---|
| **Per-bar signal generation** | The signal-generation loop iterates left-to-right in time; every per-signal compute uses `bisect_right(times, ts-1)` to slice causally. A signal at timestamp T cannot peek at any candle after T. | `backtest.py:776, 803-811, 1096-1105` |
| **Indicators (EMA, ATR, regime, swings)** | EMA/ATR precompute is a recursive formula — value at index `i` depends only on values at `i` and earlier. `detect_regime` is called with a causal window slice. ATR baseline uses a rolling window strictly INSIDE the supplied window. **No global mean/std across full dataset is computed and reused.** | `backtest.py:539-594`; `indicators.py:143-220`, especially `:188` for baseline_atrs causal |
| **Trade plan (TP/SL placement)** | `compute_ict_trade_plan` is parameter-driven — it only uses inputs supplied at call time. No forward lookups. | `ict_engine.py:788-847` |
| **CRT scan** | H4 sliding window `c4h[h4_start:h4_end]`. No forward references inside `detect_h4_crt`. | `backtest.py:1419-1429` |
| **DriftDetector** | Not instantiated in the backtest signal-generation path. It's a live-bot construct. | `adaptive_engine.py:1678-1753`; `backtest.py:789` (comment only) |
| **Normalization / scaling** | No code path computes a global statistic across the full dataset and reuses it on the tuning portion. All percentiles are inside per-signal causal windows. | Verified across `indicators.py:143-220`, `backtest.py:539-594` |

### ❌ Paths that LEAK (this is the honest part)

**🔴 HIGH LEAK 1 — Boundary label-leakage in tuning signals near the cutoff**

When a signal fires at, say, 71 hours before the cutoff, its outcome (WIN / LOSS / TP1 hit / SL hit) is determined by simulating the price action over the next 72 hours (`CRT_FORWARD_BARS=864 = 72h`). That 1 hour of forward simulation **extends INTO the held-out window**. The signal is then placed in `_tune_sigs` (because its `ts` is before the cutoff), but its label is partly determined by held-out price action. The CPCV embargo cannot fix this — embargo only purges train indices relative to test indices within the same CPCV split; the held-out indices were never passed to CPCV at all. **Effect: the last ~24-72h of tuning signal labels contain look-ahead into held-out.**

File:line: `backtest.py:4193-4202` + `walk_forward.py:245-297` + `validation.py:140-189`. Severity: HIGH.

**🔴 HIGH LEAK 2 — OGD weight bootstrap reads ALL signals (no held-out filter)**

`adaptive_engine.bootstrap_from_backtest` at `adaptive_engine.py:1111-1170` queries `backtest_signals` with **no timestamp filter** — it reads the entire history. `backtest.py:4479` saves `all_signals` (tuning + held-out commingled) under the new run_id. `backtest.py:4508-4511` then calls bootstrap with `BOOTSTRAP_AFTER_RUN` defaulting to `'1'`. The NEXT backtest reads those weights at `backtest.py:4041` via `load_backtest_ogd_weights` and starts scoring signals with weights that **already learned from held-out outcomes**. The lockbox is supposed to prevent exactly this kind of bleed; it doesn't.

File:line: `adaptive_engine.py:1111-1170`; `backtest.py:4041, 4479, 4508-4511`. Severity: HIGH. (Note: explorer trials set `BOOTSTRAP_AFTER_RUN=0` so they don't trigger this, but manual canonical backtests do.)

**🔴 HIGH LEAK 3 — Cross-config DSR pool refresh reads ALL signals**

`scripts/compute_cross_config_sr_std.py:78-95` loads all signals per run_id (no held-out filter) and runs `cpcv_summary` on the full pool (line `:287`). The resulting OOS Sharpe entered into the persisted `sr_trial_std` pool, for any run that had HELD_OUT_DAYS>0, is computed on tuning+held-out mixed. `backtest.py:4243-4250` reads that value as the next run's `sr_trial_std_for_dsr` — so the multiple-testing correction's denominator is anchored on a pool that includes held-out signal performance. **Configs tuned tuning-only still feed their held-out outcomes back into the next cycle's selection-bias correction.**

File:line: `scripts/compute_cross_config_sr_std.py:78-95, 287`; `backtest.py:4243-4250, 4479`. Severity: HIGH.

**🟠 HIGH LEAK 4 — Parameter-tuning leakage (structural / human-in-loop)**

This one isn't a code bug — it's a methodology gap. The `ACTIVE_CONFIG` at `backtest.py:4138/4161` was selected by an operator or by Optuna **after** running backtests over windows that included the now-"held-out" period. So the parameter set being held-out-tested was implicitly tuned with knowledge of the held-out period's market behavior. The held-out WR is therefore evaluating params that were partially selected to fit that window.

File:line: `backtest.py:4138, 4161, 4438-4440`. Severity: HIGH structurally; only paper soak (forward data the parameters could not have been chosen on) eliminates this.

**🟡 MEDIUM LEAK 5 — `save_to_db` writes the full pool with no marker**

`backtest.py:4479` calls `save_to_db(all_signals, ...)` — not `save_to_db(_tune_sigs, ...)`. The held-out signals get written to `backtest_signals` with no `is_held_out` flag column. `_held_out_cutoff_iso` is captured at `backtest.py:4202` and printed, but **never persisted** as a column in `backtest_runs`. This is the upstream cause of HIGH LEAKS 2 and 3 above: without a marker, downstream consumers can't filter held-out by run_id.

File:line: `backtest.py:4202, 4479`; `save_to_db` at `backtest.py:3735`. Severity: MEDIUM (root cause of HIGHs).

**🟡 MEDIUM — Silent cutoff drift**

`walk_forward.py:274-276` anchors the cutoff at `datetime.now(timezone.utc)`. If the OHLCV cache is stale or the dataset ends earlier than wall-clock (weekend, paused bot, multi-day queue), the realized held-out window can be smaller than `HELD_OUT_DAYS` days — possibly empty. There's no assertion that the dataset actually extends to now_utc; only the print line at `backtest.py:4203-4204` surfaces the counts. **You can think you have 90 days held out and actually have 12.**

File:line: `walk_forward.py:274-276`; `backtest.py:4196-4210`. Severity: MEDIUM.

**🟡 MEDIUM — Docstring oversells the guarantee**

`walk_forward.py:251-258` describes `split_held_out` as the "operational primitive for the Phase C held-out lockbox protocol: optimization/Optuna touches only the tuning portion; held-out is reserved for one-shot final validation per promotion." This phrasing suggests true held-out semantics. The actual implementation cannot enforce that signal generation was confined to the tuning window. **The name "lockbox" is aspirational, not enforced.**

File:line: `walk_forward.py:251-258`. Severity: MEDIUM (operator-misleading).

### Honest summary

The careful **per-signal causal discipline** is genuinely good. Indicators, regime detection, trade plans, the CRT scan — all clean. So if you only care about "do tuning signals see future tuning bars?" the answer is **no, they don't**.

But if you care about "is the held-out window untouched by anything that influences tuning?" the answer is **no, it isn't**:
- Tuning labels are computed using forward simulation that crosses into held-out (24-72h fuzzy boundary)
- OGD weights persist across runs and bootstrap from a held-out-commingled pool
- The DSR pool denominator is computed from held-out-commingled signals

## 3. HOW IT INTERACTS WITH CPCV

### Plain language

CPCV (Combinatorial Purged Cross-Validation) and HELD_OUT_DAYS are **not** double-testing OOS on overlapping data. CPCV runs only on tuning signals; held-out gets exactly one separate single-window evaluation with no CPCV folds. They are complementary.

### Mechanism verified

| Item | Status | File:line |
|---|---|---|
| Primary CPCV pool | `cpcv_summary(_tune_sigs, ...)` — tuning only when HELD>0 | `backtest.py:4305` |
| 12-window walk-forward (WFV) | `walk_forward(_tune_sigs, ...)` — tuning only | `backtest.py:4421` |
| Held-out evaluator | `held_out_summary(_held_sigs, ...)` — one-shot, single-window, no CPCV folds | `backtest.py:4428` |
| Print report | `print_report(_tune_sigs, ...)` — tuning only | `backtest.py:4212-4213` |
| OGD walk-forward | `_wfv_ogd_input = _tune_sigs` when HELD>0 | `backtest.py:4461` |
| Number of CPCV splits | C(5,2)=10 splits regardless of HELD_OUT_DAYS, unless n<5 | `validation.py:83-85, 223` |
| `n_oos_per_fold` formula | `max(1, round(n * 2 / 5))` where `n = len(_tune_sigs)` — correctly reflects tuning-only pool size | `validation.py:666` |

### The one subtle CPCV interaction

When you turn on HELD_OUT_DAYS=90 on a 365-day window, your tuning pool shrinks by ~25%. PSR/DSR include a `sqrt(T-1)` factor. So **PSR/DSR drop slightly by mechanical sample-size effect, not by strategy quality change**. You should not compare PSR/DSR readings across runs with different HELD_OUT_DAYS settings without accounting for this — they are not directly comparable.

Also, the embargo at `validation.py:140-189` computes its time-span from `_tune_sigs` only when HELD>0, so the absolute embargo length is slightly tighter than on the full-pool case (~25% shorter). Small effect, but it's in the leak-friendly direction. Not urgent unless HELD grows further.

## 4. THE EXPLORER QUESTION — TPE search and gates

### Short answer

**Yes**, if you set `HELD_OUT_DAYS=90` in the explorer service environment, TPE's search and the PASS/FAIL gates **will be computed only on the tuning portion**. The held-out window is NOT directly visible during the search itself (signal generation is causal at per-signal level).

**BUT** the explorer is **held-out-deaf** in three architectural ways that limit how much the lockbox actually constrains promotions.

### What's clean

| Item | What it does | File:line |
|---|---|---|
| Env passthrough | `_params_to_env` does `env = os.environ.copy()` first; `HELD_OUT_DAYS` propagates unchanged | `scripts/autonomous_explorer.py:603-636` |
| Per-trial backtest reads HELD_OUT_DAYS at import | Subprocess sees the env var; signal generation/CPCV behaves as in §1 and §3 above | `backtest.py:253, 4193-4210` |
| TPE objective sees only tuning-only metrics | `cpcv_mean` parsed from `WR (CPCV) mean=...` line, which is tuning-only when HELD>0; `_objective` uses this | `scripts/autonomous_explorer.py:680-689, 1359-1379` |
| PASS/FAIL gate uses only tuning-only metrics | `_verdict()` checks `n / cpcv_mean / cpcv_q05 / dsr` — all tuning-only | `scripts/autonomous_explorer.py:748-759` |
| `BOOTSTRAP_AFTER_RUN=0` on trial subprocesses | Explorer trials don't pollute the OGD bootstrap pool (avoids HIGH LEAK 2 from §2) | `scripts/autonomous_explorer.py:610` |
| `WRITE_CPCV_VERDICT=0` on trial subprocesses | Trial verdicts don't overwrite the live `bot_state.latest_cpcv_verdict` | `scripts/autonomous_explorer.py:616` |
| `config_hash` includes HELD_OUT_DAYS | Two trials with different HELD_OUT_DAYS get different hashes — reproducibility check works correctly | `backtest.py:3886` |

### What's broken / weak

**🟡 The explorer's regex never parses the held-out result.**
`_run_backtest` at `scripts/autonomous_explorer.py:680-691` extracts 8 metrics (n, wr, cpcv_mean, cpcv_std, cpcv_q05, sharpe, dsr, walltime). It does **not** parse the `[PHASE C GATE]` line. The held-out WR, gap_pp, and Wilson CI are printed by backtest.py and immediately discarded by the explorer.

**🟡 The trials DB has no held-out columns.**
The INSERT at `scripts/autonomous_explorer.py:1218-1230` writes only the 8 tuning-only metrics. You cannot run `--status` or any post-hoc analytics on the trials DB to answer "which trials overfit to tuning?" — held-out signal was computed and thrown away.

**🟡 Pareto archive is held-out-blind.**
`_update_pareto_archive` at `scripts/autonomous_explorer.py:1259-1269` records the same 8 tuning-only metrics. No `held_out_wr`, no `gap_pp`. Two configs with identical tuning CPCV but vastly different held-out generalization look identical in the archive.

**🟡 Auto-promotion eligibility is held-out-blind.**
`_eligibility_check` at `scripts/autonomous_explorer.py:971-1001` gates only on tuning-only metrics. A trial with stellar tuning CPCV but terrible held-out verdict will pass eligibility, burn ~22 min on the reproducibility re-run, and only THEN hit `promote_baseline.py`'s held-out gate (`promote_baseline.py:218-340`) as a final soft veto.

**🟢 BUT — the soft veto at promotion time does work** if `HELD_OUT_DAYS` is set in the parent env when the explorer service starts. The explorer's `_auto_promote` (line `:1108-1121`) does NOT pass `--held-out-days` on the command line, but `promote_baseline.py:361` falls back to `int(os.environ.get('HELD_OUT_DAYS', '0'))`. Since the explorer subprocess inherits the parent env unchanged, the gate fires correctly.

### Honest summary

Yes, your TPE search and per-trial gates run on tuning-only metrics. No, the explorer does not "learn to prefer held-out-robust configs" — held-out outcomes never enter its objective function. The held-out lockbox acts as a final post-hoc veto at auto-promotion time, not as a search-shaping signal.

## 5. HOW TO USE IT PROPERLY — Workflow

Given the limitations above, here is the workflow that gets you the most honest answer the current code can deliver:

### Setup

1. **Decide HELD_OUT_DAYS.** With 365 days total, the standard quant practice is roughly 60-90 days held out (~17-25%). 90 is a defensible choice. **Don't go above 120** — your tuning pool shrinks below ~245d and CPCV folds get thin.

2. **Make sure the OHLCV cache is fresh.** Run a small backtest with `--fresh` to refresh cached candles to the latest Binance data. Otherwise the silent-cutoff-drift gap from §2 can shrink your realized held-out window.

3. **Set the env var at the explorer service level** (not just in your shell), so promote_baseline.py's held-out gate fires correctly:
   ```
   # In deploy/env.explorer or wherever the service env lives
   HELD_OUT_DAYS=90
   ```

### Workflow A — One-shot validation of an existing pin

If your goal is "I have a promoted config; does it look honest on data the operator hadn't seen at promote-time?":

1. `cp data/baseline_pin.json /tmp/pin_snapshot.json` (backup)
2. Export the current pin's env exactly (or use `scripts/validate_baseline_held_out.py` which does this for you)
3. Run `HELD_OUT_DAYS=90 python3 backtest.py` once
4. Read the `[PHASE C GATE]` line in the output. The verdict will be ROBUST / BORDERLINE / OVERFIT
5. Read the `gap_pp` value — the difference between tuning WR and held-out WR
6. A `gap_pp ≤ 8` and held-out WR ≥ 50% = **a defensible result** (per promote_baseline.py's default thresholds)

### Workflow B — Run a NEW explorer search with held-out enforcement

If your goal is "find a new config, evaluating it on a held-out window":

1. Set `HELD_OUT_DAYS=90` in `deploy/env.explorer` (so trial subprocesses inherit it via service env)
2. Start the explorer: `sudo systemctl start tradeai-explorer`
3. **Important caveat:** the TPE search won't actively learn from held-out (§4). It will only see tuning-only metrics. The held-out gate is a **veto at promotion time**, not a search guide.
4. Watch for `[promote]` log lines saying "skipped:held_out_overfit" — those are promotions blocked by the lockbox
5. After the session, manually re-run `python3 scripts/validate_baseline_held_out.py --run-id <RUN>` for any candidate to get the held-out report explicitly

### How to read the result honestly

The held-out WR alone does NOT tell you "this config is genuinely good." It tells you:

- **If held-out WR ≥ tuning WR ± 5pp:** the config probably isn't drastically overfit to the tuning period. Necessary but not sufficient evidence.
- **If held-out WR << tuning WR (e.g., gap >10pp):** likely overfit. Reject regardless of tuning CPCV.
- **If held-out n < 5:** insufficient sample; the verdict is `INSUFFICIENT_SAMPLE` per `validate_baseline_held_out.py:17-19`. Don't draw conclusions either way.

**What it does NOT tell you:** whether the config will work in LIVE. Held-out is still on data that has been observed by the operator and by Optuna at various points in the development cycle (HIGH LEAK 4 from §2). Only paper signals on truly forward data answer the LIVE question.

## 6. HONEST LIMITS — What held-out does NOT prove

Even done correctly, a held-out test on the same 365-day file does not deliver clean out-of-sample evidence. Here's how it compares to the paper soak.

### Held-out test (current implementation)

- **Sample window:** A chronologically-recent subset of the same 365 days the strategy was developed on.
- **Independence from tuning:** Partial. Per §1-§2: tuning signals near the boundary contain look-ahead labels; OGD weights and DSR pool denominator are commingled across the boundary; the parameter set was implicitly selected with knowledge of the held-out period.
- **Sample size:** Typically n=20-40 signals over 90 days at current CRT frequency — wide Wilson CI, often inconclusive.
- **Evidence strength:** **Weak-to-moderate.** A passing held-out verdict reduces the probability of gross overfitting but does not eliminate it.

### Paper soak (forward signals)

- **Sample window:** Data that has been generated AFTER the strategy was committed; truly forward in time.
- **Independence from tuning:** **Strict.** The strategy parameters were locked before this data existed. No operator could have selected for this period.
- **Sample size:** Will accumulate to n=30 over ~3-4 months at current frequency.
- **Evidence strength:** **Strong.** This is the only truly out-of-sample evidence in the system.

### The honest comparison

| Property | Held-out test | Paper soak |
|---|---|---|
| Forward-in-time data | ❌ No (recent past, but past) | ✅ Yes (truly forward) |
| Operator never saw this data | ❌ Visible in dashboards, news, gut feel | ✅ Generated after commit |
| Optuna never tested on this | ❌ Could have during prior sessions | ✅ Cannot, by construction |
| Boundary leakage from labels | ❌ ~24-72h fuzzy boundary | ✅ Zero |
| OGD weights independent | ❌ Weights bootstrap-commingled | ✅ Live weights are separate state |
| Wait time | Instant (one backtest re-run) | Months (1-3 months for n=30) |
| Verdict strength | Approximate, sanity-check | Statistically meaningful |

**Bottom line:** A held-out test is a useful sanity check that you can run instantly. It is **not** a substitute for the paper soak. The project's LIVE-clearance gate correctly requires the paper soak (n≥30 closed forward signals) precisely because held-out alone is too leaky to bet capital on.

## 7. Should you use HELD_OUT_DAYS today?

### Honest verdict

**YES** for ongoing development — turn it on at the explorer service env (`HELD_OUT_DAYS=90`). You get:
- A real soft veto on the most overfit auto-promotions
- A `[PHASE C GATE]` print line on every backtest for manual sanity-checking
- A clean tuning-only CPCV pool (no held-out signals polluting the folds)

**NO** for "I am about to flip LIVE because held-out cleared 95% WR." The leaks identified in §2 mean a passing held-out verdict is necessary but not sufficient. The paper soak is the real gate.

### What would need to change to make held-out trustworthy as "true" OOS

These are the fixes that would actually deliver a data lockbox. The audit explicitly recommends them; none are implemented:

1. **Truncate OHLCV at the cutoff for tuning runs.** Filter `c4h/c1h/c5m` arrays at `backtest.py:4114-4116` to `[<cutoff_epoch]` for the tuning track, with a separate cache key including HELD_OUT_DAYS. Recommended by code-path agent.
2. **Run a SEPARATE one-shot signal generation pass over the full window only at final validation.** Locked params, then evaluate on the untouched held-out tail. Recommended by code-path agent.
3. **Persist `held_out_cutoff_epoch` to `backtest_runs`** + tag each `backtest_signals` row with `is_held_out`. Lets downstream consumers (`bootstrap_from_backtest`, `compute_cross_config_sr_std`) filter by held-out boundary. Recommended by leakage agent (closes HIGH LEAK 2 and 3).
4. **Add held-out columns to trials table + Pareto archive.** Lets the explorer record + retrieve held-out metrics. Recommended by explorer agent.
5. **Modify explorer's `_objective` to penalize wide tuning-vs-held-out gaps.** Phase-D-style change; would make TPE prefer held-out-robust configs. Recommended by explorer agent.
6. **Anchor cutoff at `last_signal_ts` (or last_bar_ts) rather than wall-clock now.** Fixes silent-cutoff-drift. Recommended by code-path + CPCV agents.
7. **Drop tuning signals where `ts + forward_horizon > cutoff`** before feeding `_tune_sigs` into CPCV. Closes the 24-72h boundary-label-leakage HIGH. Recommended by CPCV agent.

Until those ship, treat `HELD_OUT_DAYS` as a *useful sanity check with known leaks*, not as a *true held-out lockbox*.
