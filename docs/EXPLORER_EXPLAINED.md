## 1. SEARCH METHOD — How does it decide what to try next?

**It uses Bayesian optimization, specifically Optuna's TPE sampler.** Not random, not grid, not exhaustive.

**File:line:** `scripts/autonomous_explorer.py:1394-1398`
```python
study = optuna.create_study(
    study_name=study_name, storage=storage,
    sampler=optuna.samplers.TPESampler(seed=None),
    direction="maximize", load_if_exists=True,
)
```

### What TPE actually does (in plain English)

TPE (Tree-structured Parzen Estimator) is a Bayesian search. It maintains two distributions:
- **L(x):** parameter values from the trials that scored ABOVE the running median
- **G(x):** parameter values from the trials that scored BELOW

For each new trial, TPE samples parameter values that maximize the ratio L(x)/G(x) — i.e., values that look more like the good trials and less like the bad ones. So it **focuses on regions near configs that already scored well**, but it also explores enough to find new basins (the TPE algorithm has a built-in exploration term).

Compared to alternatives:
- vs **random search:** TPE is more sample-efficient — it usually finds good configs in 100-200 trials where random search needs 1000+.
- vs **grid search:** TPE doesn't waste trials on boring grid points; it concentrates around productive regions.
- vs **gradient methods:** TPE doesn't need derivatives, so it works with discrete/categorical parameters (which the bot has many of, like `CRT_TP1_MODE ∈ {dynamic, fixed_1r, min_1r}`).

### Persistence

Optuna saves the study state to `data/optuna_study.db`. If a session is interrupted, the next start with `load_if_exists=True` resumes from the same study — TPE remembers what it has tried.

### Honest weakness

**TPE is NOT a true random sample of parameter space.** It clusters around productive regions. This has a knock-on effect on the DSR multiple-testing math (§6 / §8 below) — the standard deviation of Sharpe values across TPE trials is **tighter** than it would be under random search, so the formula's penalty for "you tested N candidates" is calibrated for a different statistical regime than what TPE actually delivers. The project's design accepts this as a known limitation.

## 4. HOW IT SCORES — What metric ranks configs?

### Two-step process

**Step A — gate check** (binary PASS/FAIL/ERROR): `_verdict()` at `scripts/autonomous_explorer.py:748`

A trial PASSES only if ALL FOUR are satisfied:
- `n ≥ EXPLORER_N_MIN` (signal count)
- `cpcv_mean ≥ EXPLORER_WR_MIN` (cross-validated WR %)
- `cpcv_q05 ≥ EXPLORER_Q05_MIN` (worst-case fold WR %)
- `dsr ≥ EXPLORER_DSR_MIN` (Deflated Sharpe %)

Defaults at `scripts/autonomous_explorer.py:137-142` (operator can override via env):
- `EXPLORER_N_MIN = 30` (but operator currently runs with =120 per session env)
- `EXPLORER_WR_MIN = 60.0`
- `EXPLORER_Q05_MIN = 50.0`
- `EXPLORER_DSR_MIN = 95.0`

**Step B — Optuna objective score** (real number, drives TPE's next sample): `_objective_factory` at line 1195, score formula at lines 1359-1379.

```
score = cpcv_mean + alpha * log(max(1, n))     if PASS
score = cpcv_mean - 30 + alpha * log(max(1, n)) if FAIL with cpcv_mean known
score = -100                                    if ERROR / no metrics
```

`alpha = N_BONUS_ALPHA = 2.0` by default. The `log(n)` bonus exists because LIVE clearance requires ≥30 closed paper signals — without it, TPE would converge to ultra-high-WR low-frequency configs and the operator would never accumulate enough signals to qualify for LIVE.

### What this means in practice

- **Quality dominates frequency.** CPCV mean WR is the primary signal. A 1-pp WR improvement is worth `~3-5 extra signals` of `log(n)` bonus at typical n.
- **DSR is a GATE, not a score component.** A trial with high CPCV but DSR=94% gets verdict=FAIL and `score = cpcv_mean - 30 + n_bonus` — TPE will still steer somewhat toward it (it's "less bad" than a 50% WR FAIL) but it's actively penalized vs a PASS.
- **Errors get -100 sentinel.** TPE actively steers AWAY from parameter regions that timeout or crash.

### Honest weakness

The objective optimizes against `cpcv_mean` directly, not DSR. Two configs with identical CPCV mean but different DSRs would tie in TPE's view. The DSR threshold is only checked as a binary gate. **TPE is not directly optimizing the project's actual LIVE-clearance criterion** — it's optimizing CPCV with an n bonus and using DSR as a yes/no filter.

## 5. ACCEPT / REJECT — When does a config "stick"?

**Default behavior of every trial:**

Every trial is a one-shot test. The backtest subprocess writes its results to `data/signals.db::backtest_runs` + `backtest_signals`. The explorer records the trial in `data/explorer_learning.db::trials`. **Nothing operationally important changes — yet.**

### Auto-promotion (the only path where a config "sticks")

A trial gets promoted to the live baseline ONLY if it passes an **8-criteria gate** + **reproducibility re-run** + **daily/soak cap** (`scripts/autonomous_explorer.py:1166 _try_auto_promote`).

The 8 criteria (lines 244-253 `PROMOTE` dict):
1. `dsr ≥ 95%`
2. `cpcv_mean` beats pin by ≥ 0.5pp
3. `sharpe` beats pin by ≥ 0.02
4. `cpcv_std` doesn't widen by > 1.0pp
5. `cpcv_q05` doesn't drop by > 1.0pp
6. `n` within ±20% of pin's n
7. **Reproducibility:** run the same config a SECOND time. Config_hash must match exactly + cpcv_mean within ±0.5pp tolerance.
8. Daily cap: ≤2 promotions per UTC day, ≥24h between promotions.

If all 8 pass:
- `promote_baseline.py` writes `data/baseline_pin.json` with the new config_hash + metrics
- A row goes into `tune_history` audit table
- `compute_cross_config_sr_std.py --scanner-mode crt_only` re-runs to refresh the DSR pool
- A Telegram message fires

Otherwise (the overwhelming majority of trials): nothing persistent. The backtest_runs row is cleaned up. The explorer trial row remains as a record.

### Empirical reality

In all 3,865 trials, there have been **44 PASS verdicts** (the easier early-session gates) and the auto-promotion path has run rarely. Run-3704 was **NOT auto-promoted** — it was operator-manually picked from my "top 5 by DSR" reports, ran manually through `promote_baseline.py` (not through `_try_auto_promote`), and the operator made the call.

## 6. OVERFITTING GUARDS — The most important question

### a) Walk-forward / out-of-sample testing — YES, always

Every backtest the explorer runs uses **Combinatorial Purged k-Fold Cross-Validation (CPCV)** from `validation.py` per López de Prado (2018). Configuration:
- K = 5 groups, k = 2 test groups → C(5,2) = 10 splits per backtest
- Embargo = 2% of timeline
- Reports `cpcv_mean WR`, `cpcv_std`, `cpcv_q05`, `cpcv_sharpe`

There's ALSO a non-CPCV "walk-forward IS/OOS" split with a fixed wall-clock boundary that the report prints. The OOS boundary on the current Run-3704 backtest is 2025-11-03.

Both checks happen on EVERY backtest. The explorer can't skip them.

### b) Does DSR penalty account for ALL explorer trials? — NO. This is the honest weakness.

The DSR formula needs two inputs:
- `N` = number of trials in the selection space
- `σ_SR` = standard deviation of Sharpe across those trials

In the current code:
- `N` = `COUNT(DISTINCT config_hash) FROM backtest_runs` only (the formal backtests, currently ~33)
- `σ_SR` = computed by `compute_cross_config_sr_std.py` from those same 33 configs (currently 0.138)

**The ~2,295 distinct explorer trials in `explorer_learning.db` are NOT counted.** This is INTENTIONAL per CLAUDE.md §3 ("Explorer trials are NOT counted in DSR pool — prevents death spiral"). The reasoning: counting every trial would inflate the penalty to the point where no strategy ever clears the gate.

**My cycle #2/#3 analysis showed** the omission is actually conservative-direction: when the proper σ for the full trial population is used (0.082 from the 899 qualified explorer trials), the DSR rises from 96.5% to ~97.8%. So the project's choice doesn't over-state DSR — it under-states it slightly. But **a strict Bonferroni reading at α=0.05/810 would NOT clear** the strategy at the current observed Sharpe. The project explicitly uses DSR (Bailey/López de Prado) as the gate, not Bonferroni.

### c) Locked anti-patterns — YES, hard-enforced at session start

Lines 162-190 `ANTI_PATTERN_LOCKS` + `CRT_ANTI_PATTERN_LOCKS`. Asserted at line 1385 via `_assert_anti_pattern_locks()`. If any anti-pattern has been silently re-enabled in source code, the explorer **refuses to start** (raises `RuntimeError`).

### d) What stops over-tuning to the same 365 days?

This is the **biggest residual concern**, and the project's mitigations are:

1. **CPCV with embargo** — each backtest splits the 365 days into 10 OOS folds with a 2% gap to prevent label leakage between adjacent folds. Better than naive train/test but NOT a true held-out window.

2. **Walk-forward IS/OOS split** — fixed-boundary 80/20 split also reported. If WF-gap (IS WR - OOS WR) > 10%, the report flags it.

3. **DSR / PSR multiple-testing correction** — penalizes high Sharpe in proportion to how many candidates were tried. As discussed in (b), this is incomplete coverage.

4. **`HELD_OUT_DAYS` env var** — `backtest.py:253` reads this. Operator can force a held-out window. **Currently set to 0** (no held-out lockbox).

5. **Cross-session repeat:** the explorer keeps re-running the same 365-day data. **No mechanism rotates the data window or holds out untouched segments.** This is the honest gap. With 2,295 distinct configs tested on the same 365 days, the probability of finding one config that wins by luck is real.

### Honest assessment

The overfitting guards are MULTIPLE LAYERS but NONE are airtight:
- CPCV catches within-window leakage. ✓
- DSR penalizes search breadth. ✓ but with the gap noted in (b).
- Anti-pattern locks prevent the worst known historical mistakes. ✓
- A true held-out lockbox over a CLEAN UNTOUCHED window does NOT exist. ✗ — this is the biggest remaining concern.

The project's mitigation for that last gap is **paper soak**: any config promoted as a baseline must accumulate ≥30 closed paper signals (on live forward data, never seen by the backtest) before going LIVE. Paper signals ARE the held-out lockbox, just in real-time form.

## 7. ISOLATION — Can the explorer corrupt the LIVE system?

**No — by three explicit mechanisms.**

### a) `BOOTSTRAP_AFTER_RUN=0` — protects live OGD weights

Every explorer-launched subprocess sets this env var (`scripts/autonomous_explorer.py:610`):
```python
env["BOOTSTRAP_AFTER_RUN"] = "0"
```

`backtest.py:4470-4473` honors this flag: when `=0`, the post-run weight write to `backtest_token_weights` is SKIPPED. Result: trial backtests never touch the live `token_weights` table OR the bootstrap weight pool. **Verified by `adaptive-learning-code-reviewer` in cycle #1.**

### b) `WRITE_CPCV_VERDICT=0` — protects live verdict

Every explorer subprocess also sets (`scripts/autonomous_explorer.py:616`):
```python
env["WRITE_CPCV_VERDICT"] = "0"
```

`backtest.py:4298` honors this: when `=0`, the `bot_state.latest_cpcv_verdict` write is SKIPPED. Result: trial backtests can't pollute the OGD learning-rate gate with FAIL verdicts that don't apply to the current pin.

### c) `baseline_pin.json` — protected by the 8-criteria + reproducibility gate

The ONLY code path that writes `data/baseline_pin.json` is via `_try_auto_promote` → `_auto_promote` → `subprocess.run` calling `scripts/promote_baseline.py --auto`. This is gated by all 8 criteria from §5, including a reproducibility re-run that must match the original config_hash exactly.

There is no other write path. `EXECUTION_MODE=LIVE` is NEVER touched by the explorer.

### d) Backtest_runs row cleanup

After each trial, the explorer cleans up its `backtest_runs` row to keep the formal pool clean (`scripts/autonomous_explorer.py:1015 _cleanup_run_row`). Only auto-promoted runs survive in `backtest_runs`. This is what keeps the DSR pool from being polluted by 3,865 explorer trial rows.

### Honest weakness

If `BOOTSTRAP_AFTER_RUN` or `WRITE_CPCV_VERDICT` were accidentally removed from `_params_to_env()` (`scripts/autonomous_explorer.py:603-636`), the next explorer session would silently start writing to live tables. There is no runtime assertion that these flags are set — the protection relies on code review. **Cycle #4 verified they're still in place** but a future PR could remove them without a test failure flagging the regression.

|---|---|---|
| Bot's reported DSR | **96.3% PASS** | Run #3708 backtest log |
| n in DSR pool denominator | 33 | `bot_state.cross_config_sr_pool` |
| σ in DSR pool | 0.138 | `compute_cross_config_sr_std.py` output |

### Does the reported DSR account for the full ~2,210-config selection process?

**No.** The bot's DSR formula counts only the 33 distinct config_hashes in `backtest_runs`. The 2,177 explorer-only config_hashes are NOT in the denominator. This is the design choice from CLAUDE.md §3 ("explorer trials NOT in DSR pool").

### What's the honest selection-adjusted number?

From my cycle #2 analysis (re-verified in cycle #3 and #4):

| Interpretation | N used | σ used | Resulting DSR |
|---|---|---|---|
| Bot's reported (project methodology) | 33 | 0.138 (deduped pool) | **96.3%** ✓ clears 95% |
| Full explorer population, proper σ | 810 | 0.082 (population spread) | **~97.8%** ✓ clears (HIGHER, not lower) |
| Hypothetical mix-and-match | 810 | 0.138 (wrong combination) | ~85.5% ✗ — but this combo is methodologically wrong |
| Strict Bonferroni at α=0.05/810 | required z = 3.85 | observed z = 3.42 | ✗ would NOT survive |

### The honest plain-language summary

Run-3704's reported DSR of 96.3% is computed against a deliberately-narrow pool (only formally-promoted configs, not explorer trials). The cycle #2 analysis showed that **using a wider pool with the proper σ produces a HIGHER DSR**, not lower — because TPE-guided exploration clusters trials in productive regions, the standard deviation across them is TIGHTER than across the deduped formal pool. So the project's stated DSR is conservatively biased, not optimistically biased.

A STRICTER frequentist test (Bonferroni multiple-testing at the full 810-trial surface) would NOT clear the strategy. The project explicitly uses DSR (Bailey/López de Prado 2014), not Bonferroni.

**My honest read: Run-3704 clears the project's chosen statistical gate, with the caveat that "the project's gate is more permissive than a strict Bonferroni reading."** This is not hidden — it's the standard quant industry convention (Bailey/LdP's deflation is the explicit alternative to the over-conservative Bonferroni).

### Selection-bias I cannot quantify

The operator-side selection — me showing you top-5 reports across multiple windows, you picking trial 3777 from those — adds a **second-order selection event** that is NOT captured in either pool count. The honest n_effective for "trials the operator could have promoted" is probably closer to **the union of all top-N reports across multiple sessions × multiple metric orderings ≈ 50-100 distinct candidates considered**. At N=50, σ=0.082, the math still clears 95% DSR easily (~99%). At N=100, still ~99%. So this layer of selection bias doesn't change the verdict — DSR clears under any reasonable accounting of the surface.

## Summary — What's Strong, What's Weak

### Strong
- TPE Bayesian search is genuinely sample-efficient (1,000 trials = roughly 5,000-10,000 random-search equivalent)
- Anti-pattern locks are hard-enforced at session start
- 3-layer isolation (`BOOTSTRAP_AFTER_RUN=0`, `WRITE_CPCV_VERDICT=0`, no `baseline_pin.json` write path except via 8-gate auto-promote)
- CPCV with embargo on every backtest catches within-window leakage
- Reproducibility re-run before any auto-promotion catches non-deterministic configs
- Daily promotion cap (2/day) + 24h soak prevents pin churn

### Weak / honest gaps
1. **No clean held-out lockbox.** Same 365 days hammered 2,295 times. Paper soak is the only true OOS check.
2. **DSR penalty doesn't count explorer trials.** Intentional design choice; honest direction is conservative not optimistic, but Bonferroni would not clear.
3. **TPE non-uniform sampling.** σ across explorer trials is tighter than under random search; DSR formula assumes statistical regime that TPE doesn't deliver.
4. **`BOOTSTRAP_AFTER_RUN` / `WRITE_CPCV_VERDICT` isolation flags depend on code-review discipline.** No runtime assertion that they're set.
5. **Operator-side manual top-N selection** adds a second-order selection bias not captured by any code.
6. **Objective optimizes CPCV mean, not DSR.** TPE doesn't directly optimize the LIVE-clearance criterion.

### The single most important truth

**The strategy's edge is not statistically proven by the backtest alone.** The DSR=96.3% number is honest within the project's stated methodology but a stricter reading wouldn't clear. The 30-paper-signal floor (currently 5/30) is the real proof point — paper signals are forward-looking, never seen by the backtest, and immune to all the selection-bias concerns above. **LIVE-clearance correctly waits on that floor, regardless of how high backtest DSR climbs.**
