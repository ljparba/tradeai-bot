**Location:** `data/signals.db` (single file containing both `backtest_runs` and `bot_state`)
**Severity:** MODERATE — partially mitigated; worst case is DSR skipped rather than incorrectly computed

This is BETTER than the pre-fix behavior (where `n_trials=1` would produce `E[max SR]=0` → DSR = PSR vs 0 → trivially easy to pass), but it's still incomplete: the operator gets MARGINAL instead of FAIL on an overfit strategy until enough configs re-accumulate.

**Impact:** Current state is actually FINE because the DB was re-populated (14 distinct hashes, cumulative_min_trials=27 properly seeded from prior audit C-D seeding). This risk is prospective — the NEXT DB wipe.

**Recommendation:** Write `cumulative_min_trials` to a separate JSON file outside `signals.db` (e.g., `data/bot_meta.json`) and read from BOTH. Whichever is higher wins. The JSON file is committed to git or excluded from `.gitignore`, so it survives DB wipes. ~10 lines of code.

### NF-2 (MODERATE): `cross_config_sr_trial_std` computed from only 3 CRT configs — sample std is noisy

**Location:** `bot_state.cross_config_sr_trial_std` (currently persisted value)
**Severity:** MODERATE — std estimate has ~50% relative error; no warning printed

Current persisted value: `{"value": 0.084895, "n_configs": 3}`. The 3 Sharpes are 0.2865, 0.2175, 0.1176. Sample std computed from 3 observations has a standard error of approximately `σ / sqrt(2*(n-1)) = 0.0849/sqrt(4) ≈ 0.042` — about 50% relative error. The true `sr_trial_std` could plausibly range from 0.04 to 0.13 at 95% CI.

**Impact on DSR:** With `n_trials=27` and `sr_std=0.0849`, `E[max SR] ≈ 0.0849 * f(27)`. If the true std is 0.04 (lower end), `E[max SR]` drops by ~53%, making DSR easier to pass. If the true std is 0.13 (upper end), `E[max SR]` rises by ~53%, making DSR harder to pass. The current estimate of 0.0849 is in the middle, but with 3 observations this is a wide uncertainty band.

**No warning is currently printed** when `n_configs < 5`. The text report shows `SR_trial_std=0.085` but gives no indication that this is a highly uncertain estimate.

**Recommendation:** Add a warning in `compute_cross_config_sr_std.py` when `n_configs < 5`:
```python
if len(sharpes) < 5:
    print(f"[WARN] sr_trial_std estimated from {len(sharpes)} configs. "
          f"Relative uncertainty ~{1.0/math.sqrt(2*(len(sharpes)-1)):.0%}. "
          f"Collect >=5 CRT configs for a reliable estimate.")
```
Also add a `small_n_warning` flag to the JSON blob so `backtest.py` can print the warning alongside DSR in the honest metrics report.

### NF-3 (INFO): `n_oos_per_fold` uses theoretical estimate; actual purged count can be lower

**Location:** `validation.py:659`
**Severity:** INFO — anti-conservative for PSR/DSR; marginal impact at current sample sizes

`n_oos_per_fold = max(1, int(n * n_test_groups / n_groups))` uses the theoretical expected OOS count. For K=5/k=2 with n=43: `int(43*2/5) = 17`. After purging with CRT's 48h label windows and typical ~4h inter-signal spacing, some folds lose 3-5 events, making actual counts as low as 12-14. Using T=17 instead of T=12 inflates `sqrt(T-1)` in the PSR denominator by `sqrt(16)/sqrt(11) ≈ 1.2x`.

**Impact:** At borderline WR (55-58%), overestimating T by 20-30% could push PSR from ~0.93 to 0.95+, potentially flipping a MARGINAL to PASS. Current CRT WR=48% is deep in FAIL territory, so this has no operational impact today. The concern is future: once CRT WR approaches the MARGINAL/PASS boundary.

**Recommendation:** Replace with `min(len(test_idx_last_seen), n_oos_theoretical)` where `test_idx_last_seen` is the minimum across all splits. This requires a small loop modification. Alternatively, use the actual per-fold OOS count from `splits_meta[i].n_test`.

**More specifically:** Change `n_oos_per_fold` to use the minimum actual test size:
```python
n_oos_per_fold = max(1, min(
    int(n * n_test_groups / n_groups),  # theoretical upper bound
    min((m.n_test for m in splits_meta), default=1)  # actual minimum
))
```

### NF-6 (SERIOUS): MARGINAL verdict with DSR=None is misinterpreted in the text report label

**Location:** `validation.py:804–806` (cpcv_text_report)
**Severity:** SERIOUS (interpretation wrong, not formula wrong)

The verdict line in the text report reads:
```
  VERDICT: MARGINAL   (Phase A exit: CPCV mean WR >= 58%, DSR >= 95% if computed)
```

The phrase "if computed" ambiguously covers TWO distinct cases that are NOT equivalent:
- Case A: WR in 55-58% AND DSR PASSES (>=0.95) — solid multiple-testing-survived edge
- Case B: WR >= 55% AND DSR = None — no multiple-testing correction applied at all

Both cases produce `verdict=MARGINAL`. A reader seeing `MARGINAL` in a CPCV text report and the absence of "ANTI-CONSERVATIVE" warnings might reasonably interpret this as "borderline pass with selection-bias correction applied." If DSR is None (Case B), no selection-bias correction was applied.

The `dsr_gate_applied` field in the summary distinguishes these cases, but the TEXT report at line 800-801 prints:
```
  DSR              = (skipped - n_trials_for_dsr not supplied)
```
This line is present, so a careful reader CAN distinguish. But the VERDICT line itself does not distinguish MARGINAL/DSR-applied from MARGINAL/DSR-skipped.

**Recommendation:** Add a MARGINAL sub-qualifier in the verdict line:
```python
if out.get("verdict") == "MARGINAL":
    dsr_qual = "(DSR PASS)" if out.get("dsr_gate_applied") else "(DSR NOT COMPUTED)"
    lines.append(f"  VERDICT: MARGINAL {dsr_qual}  ...")
```
This makes the critical distinction visible in the headline without requiring the reader to parse DSR's separate line.

### NF-8 (INFO): Triple-barrier INVALID sentinel uses `bin=0`, not `bin=2`

**Location:** `labeling.py:126`
**Severity:** INFO (schema inconsistency with the mission brief spec)

The brief specified `tb_bin=2` for INVALID. The implementation uses `bin=0` with `touch="INVALID"`. This means INVALID trades cannot be distinguished from TIMEOUT trades by `bin` alone — callers must check the `touch` field. The `label_outcome_aliases` helper at line 347 handles this correctly (returns `"INVALID"` for unmapped values), but any downstream code that inspects only `bin` would confuse INVALID with TIMEOUT.

**Verification:** No downstream code in `backtest.py`, `validation.py`, or `labeling.py` inspects `bin` directly for the INVALID case — they always use `outcome` or `touch`. No operational impact.

**Recommendation:** Document this in the docstring explicitly: "INVALID uses `bin=0` (same as TIMEOUT); distinguish by checking `touch=='INVALID'`."

**Observation:** The `cross_config_sr_trial_std` being computed with 3 CRT-only configs that all backtest the same 365-day window raises a data-pooling concern: the 3 configs are NOT independent (overlapping training data → correlated OOS Sharpes). The Bailey/LdP 2014 Gumbel approximation for `E[max SR]` assumes independent trials. Correlated configs understate the spread of the null distribution. However, the direction of bias is toward MORE conservative DSR (correlated configs → std may be wider than under independence because they share systematic factors) — so the current implementation is safe in the conservative direction.

**Relevant Agent:** backtest-bias-detector.

**Reason:** Data overlap between configs used to compute `sr_trial_std` is technically a violation of the independence assumption in the DSR formula. Whether this biases DSR up or down depends on the sign of the config-Sharpe correlations — worth quantifying when n_configs grows to 5+.
