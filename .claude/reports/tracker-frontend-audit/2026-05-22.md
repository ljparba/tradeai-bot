## PART B — Visualization Recommendations (the chart question)

Current state: the dashboard has **zero actual charts**. Everything is rendered as HTML divs (KPI cards, tables, fake-bar progress meters, custom "conf-breakdown" rows). No `<canvas>`, no `<svg>` plotting, no chart library.

**This is fine for ~70% of the data**, but there are six specific spots where converting to real charts would be a substantial UX upgrade.

### Recommended approach: Chart.js via CDN

- **Why:** ~50KB gzipped, no build step, single `<script>` tag, works inside the single-file Python deployment, dark-theme friendly, exact match for our use case (small dashboards with mixed chart types).
- **Why not alternatives:** ApexCharts (~150KB heavier, overkill); uPlot (smallest but needs hand-rolled tooltips); D3 (build complexity, overkill); native canvas/SVG (NIH).
- **CDN tag:** `<script src="https://cdn.jsdelivr.net/npm/chart.js@4"></script>`
- **Offline fallback risk:** acceptable — tracker is loopback-only by default; user is online when they open it. Could mirror to `static/chart.umd.js` if VPN-block ever blocks jsdelivr.

| # | Where | Current | Recommended | Why |

The dashboard tells you "best trade", "avg R:R", "win rate" but never shows the **P&L trajectory**. Every retail-grade trading dashboard has this front and center. One Chart.js line chart, data already exists in `results.profit_pct` ordered by `closed_at`. |

## What I would NOT recommend

- **Don't replace the Signal History table with a chart** — tables are the right primitive for row-level inspection.
- **Don't switch to a heavyweight charting framework** (D3, Plotly, ApexCharts). Chart.js is the right weight class for a single-file Python tracker.
- **Don't add real-time WebSocket pushes** for chart updates — current 30s polling is fine at the bot's signal frequency (~42 signals/year).
- **Don't migrate to React/Vue/Svelte** — the single-file HTML-in-Python deployment model is a feature for operator ease, not a constraint to escape.
