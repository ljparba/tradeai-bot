## CRITICAL

### C-1 — `_paper_progress` counts every OPEN signal as a "closed paper signal"
`tracker.py:2134-2137`
```sql
SELECT COUNT(*) FROM signals
 WHERE status='CLOSED'
    OR EXISTS (SELECT 1 FROM results r WHERE r.signal_id=signals.id)
```
`crypto_alert.py:687` writes `INSERT INTO results (signal_id) VALUES (?)` on EVERY signal fire (default `result='OPEN'`). Therefore the EXISTS branch matches every signal ever generated, OPEN or CLOSED. The LIVE-clearance countdown (`closed / 30`) and the ETA-to-LIVE will both be wrong the moment the bot starts firing paper signals. With the DB currently at 0 signals the bug is invisible.

Fix: drop the EXISTS clause, or constrain it to `r.result NOT IN ('OPEN', NULL)`. The correct closed-set predicate is what `_canonical_wr` uses everywhere else: `result IN ('WIN','LOSS','PARTIAL','PARTIAL_TP1','PARTIAL_TP2','EXPIRED')`.

### C-2 — OGD weight matrix in dashboard shows only 1 token (TON), not 10
`tracker.py:486-489` (`_get_adaptive_weights_raw`) reads exclusively from `token_weights`. That table has only the TON row (the only live update written so far). The other 9 tokens have full bootstrap weights in `backtest_token_weights` but the dashboard never reads that table. Result: Adaptive tab shows `is_degenerate`/`blend_pct`/`recent_wr` only for TON; operator believes the bot has no learning state for BTC/ETH/XRP/HBAR/AVAX/LINK/BNB/ADA/POL. This is the exact regression flagged in the audit prompt.

Fix: fall back to `backtest_token_weights` rows when a token has no `token_weights` row (mark them `bootstrap_phase=true` in the response so the badge can read "BOOTSTRAP" instead of "LEARNING").

### C-3 — Tracker hardcodes "PAPER mode (signal-only)" in the Honest Metrics tab
`tracker_html.py:3809-3810` — `hmExecutionMode` is set to the literal string `'PAPER mode (signal-only)'`. Nothing in the API surfaces the *actual* `EXECUTION_MODE` (`heartbeat.json` contains `"execution_mode": "PAPER"` — already available). If the operator ever flips the bot to LIVE, this tab will continue to read PAPER and silently mis-inform.

Fix: add `execution_mode` to `get_honest_metrics()` (read `os.environ.get("EXECUTION_MODE","PAPER")` or `data/heartbeat.json.execution_mode`), then render `d.execution_mode` instead of the hardcoded string.

## HIGH

### H-1 — `manual_close_signal` writes `closed_at` in NAIVE LOCAL time
`tracker.py:1834` — `now = datetime.now().strftime("%Y-%m-%d %H:%M:%S")` (no `timezone.utc`). Every other writer (`crypto_alert.py:1013,1018,1048,1304`, etc.) uses `datetime.now(timezone.utc)`. The bot's VPS runs in UTC, so today this is a no-op; but if the operator ever runs the tracker on a non-UTC host (e.g. local PC for testing) every manual close will be timestamped 8h off from auto closes, breaking equity-curve order and any `datetime('now','-N days')` window filter that touches the `results` rows.

### H-2 — Risk gauge denominator fallback is still the old LIVE cap, not PAPER
`tracker_html.py:3991` — `(po.max_risk_pct != null ? po.max_risk_pct : 0.15) * 100`. When the API responds correctly the displayed cap is fine (`1.0` in PAPER, `0.03` in LIVE per `adaptive_engine.py:123,128`). But the JS fallback is still `0.15` (the M18-removed value). If `/api/adaptive/summary` errors momentarily, the dashboard renders a `0.00% / 15.0%` cap that has not existed in the backend since the M18 fix. This is the same class of drift bug as the 2026-05-22 audit's F1/F2 — half-fixed: the happy-path is now correct, but the fallback is still wrong.

### H-3 — Open-positions gauge fallbacks are LIVE values (3/2)
`tracker_html.py:3981-3985` — `(po.max_open||3)`, `(po.max_same_dir||2)`. With `EXECUTION_MODE=PAPER` the real caps are 20 and 10. Same half-fix as H-2: happy-path correct, fallback wrong.

### H-4 — RANGING-floor formula on the dashboard does not exist in the backend
`tracker.py:460` computes `ranging_floor_raise = max(0, threshold_adj) // 3`, and `tracker_html.py:3122,3130` surfaces it as "conf floor raised in RANGING/UNKNOWN (adj=N)". The actual code at `crypto_alert.py:533-537` uses **`target_adj ∈ {-4,-2,0,+4,+7}` depending on neutral_wr**, not a divide-by-3 step. There is no `threshold_adj // 3 → floor-bump` mechanism anywhere in the codebase. This card is a fabricated derived quantity.

### H-5 — Tab pill / OGD alert label fall through to literal `'UNKNOWN'`
`tracker_html.py:3824` — `alertEl.textContent = ogd.global_alert || 'UNKNOWN'`. The backend `_ogd_health_snapshot` already initialises `global_alert: 'UNKNOWN'` on import failure. If `monitoring.py` is unavailable (e.g. circular-import broke) the dashboard says "UNKNOWN" with no further indication. Tooltip should surface `ogd.error` so the operator knows *why* it's UNKNOWN.

### M-2 — `_paper_progress` rate-source label says `backtest_run_latest` but always uses the latest run
`tracker.py:2156-2157` — the label `rate_source = "backtest_run_latest"` is *technically* what the code does, but the frontend label dictionary at `tracker_html.py:3863-3864` maps it to "latest backtest (no live data yet)" — which is fine for now but the underlying calculation `bt[0] * 30.0 / bt[1]` will return `35 * 30 / 365 ≈ 2.87/mo` instead of the previous baseline's `43/365d`. Frontend doesn't show *which* run this came from. Cosmetic but causes confusion when operator compares to CLAUDE.md's documented `43 signals / 365d` claim.

### M-3 — Bot Health Score denominators hardcoded `/40 /20 /20 /20` (S6 from prior audit)
`tracker_html.py:748,752,756,760`. The four score caps live in JS only; backend `get_intelligence` at `tracker.py:449-453` enforces the same caps using `min(round(...), 40/20)`. If the backend weights change, the HTML denominator silently rots. Add `max_*` fields to the API response and read them in JS, OR move scoring to one constants dict shared with the backend.

### M-4 — `cross_config_std.note` exposes seeding caveat verbatim (good!) but `n_configs=24` is *historical seed*, not the live count
`bot_state.cross_config_sr_trial_std` (verified: value=0.0836, n_configs=24) is the 2026-05-23 seed from the CLAUDE.md historic record. The active DB has 0 distinct configs in the pool because the DB was reset on 2026-05-25. The displayed "n=24" makes the operator believe the pool is healthy when in reality it's reading a *seeded constant* until enough new distinct configs accumulate. The note text mentions this (good), but the cell label `hmStdN` shows the raw number without a "(seeded)" badge.

### M-5 — `expiresAt` is interpreted as UTC by adding 'Z' (`tracker_html.py:2854`) but `closed_at` from manual close path is local time
H-1 root cause. Equity curve (`/api/equity-curve` query at `tracker.py:139-148`) uses `COALESCE(r.closed_at, s.timestamp) >= datetime('now', '-N days')`. SQLite's `datetime('now')` is UTC. Manual closes timestamped in local time will fall in the window incorrectly. Fix once H-1 is fixed.

### M-6 — Latest backtest report parsing is robust except for one ambiguity
`_parse_honest_metrics_from_report` at `tracker.py:1899-1912` — verified against `backtest_reports/Run82_20260526_0702.txt`. All regexes match. One latent risk: `r"std=([\d\.]+)%"` is generic; it currently happens to first match the CPCV-WR std on line 274 (`std=7.93%`) and that's what gets used as `cpcv_wr_std`. If the report format ever inserts another `std=N%` before the WR line, the wrong value will be picked up. Anchor it to follow `mean=...%\s+`.

### M-7 — `get_baseline_pin` displays "Run-82 but matches the pinned config_hash" — CORRECT
Verified the path through `tracker.py:2099-2110`: Run-82 (latest) has identical `config_hash` (d77dfcc...) to pinned Run-81 → status="ok", message says hash-matched. Both runs are the same config so this is honest.
