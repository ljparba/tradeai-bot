## NEW FINDINGS (cycle-9)

### N-1 — Counter-direction Wyckoff phase tags dominate live CRT signal mix (MEDIUM, NEW)
- **Files:** crt_engine.py:829-934 (`detect_wyckoff_context`) + entry_type tagging
- **Observation:** ALL 5 live CRT signals are SELL signals tagged with `H4_CRT_OB_ACCUMULATION` (4 of 5) or `H4_CRT_OB_MARKDOWN` (1 of 5). Per the Wyckoff schema, SELL setups should pair with DISTRIBUTION or MARKDOWN. ACCUMULATION + SELL is the "counter-trend reversal" case the strict filter would reject.
- **Sample size caveat:** n=5 is too small to draw a conclusion. The CRT scanner is empirically permissive on counter-trend setups (WYCKOFF_PHASE_FILTER=off by design — strict mode empirically hurt -5.22pp WR). But the observation that the FIRST 5 live CRT signals are 80% direction-misaligned with their tagged Wyckoff phase deserves visibility.
- **Recommendation:** After 30+ closed CRT signals accumulate, run a per-phase WR query: `SELECT entry_type, COUNT(*), SUM(CASE WHEN status='WIN' THEN 1 ELSE 0 END)*100.0/COUNT(*) AS wr FROM signals WHERE source='H4_CRT' AND status IN ('WIN','LOSS') GROUP BY entry_type`. If counter-direction tags consistently underperform direction-aligned tags, revisit whether `WYCKOFF_PHASE_FILTER=loose` (reject only TRANSITION) recovers some WR without dropping too many signals.

### N-2 — `detect_wyckoff_context` `pre_range_trend` uses single-bar snapshots → noise vulnerable (LOW, RE-RAISE)
- **File/Line:** crt_engine.py:898-912
- **Detail:** `pre_close = c[pre_range_idx]` and `start_close = c[range_start_idx]` are SINGLE bars at the boundaries of `2*recent_n` / `recent_n` windows. A single anomalous close (wick day, news spike) flips `pre_range_trend` between UP/DOWN/FLAT.
- **Already noted as L-2 in cycle-8 audit.** Severity unchanged; small impact while filter is OFF. Should use a smoothed average (e.g. EMA10 or median of 5 bars at each anchor) when filter=loose/strict ever returns.

### N-3 — Live `detect_wyckoff_context(c4h)` passes the full closed-bar cache, not a windowed slice (LOW, NEW)
- **File/Line:** crypto_alert.py:921 (`wyckoff_context = detect_wyckoff_context(c4h)`)
- **Status:** Not a bug today — live cache is real-time-bounded so no lookahead is possible. But after C-3 fix made the backtest call `detect_wyckoff_context(c4h_win)` (bounded slice), the LIVE path now has DIFFERENT input shape than backtest. The function self-bounds via `closes[-window_n:]` internally (line 862), so the final analysis window IS the same size in both — `min(n, WYCKOFF_H4_LOOKBACK=120)`.
- **Why LOW not MEDIUM:** Internal self-slice means outputs are identical. But a future change to `detect_wyckoff_context`'s bounding logic could silently desync live vs BT. Add an explicit slice at the live call site for defense-in-depth: `detect_wyckoff_context({k: v[-WYCKOFF_H4_LOOKBACK:] for k, v in c4h.items()})`.

### N-4 — Live `c1h_live` is read from `STATE[token]["candles"].get("1h", {})` but no `[:-1]` slice applied (LOW, NEW)
- **File/Line:** crypto_alert.py:4032 (`_c1h_live = STATE[token]["candles"].get("1h", {})`) + line 4081 (`get_trend(_c1h_live.get("closes", []))`)
- **Detail:** When computing `_crt_trend_1h`, the 1H candle array INCLUDES the forming bar at index [-1]. `get_trend` reads the last close. So the 1H trend used as both CRT's `trend_1h` AND its OGD `trend_strength` feature reflects the forming bar's mid-formation close — which can repaint by the time the bar closes.
- **Impact:** Marginal — `get_trend` typically uses EMA50/200 (smoothing) so a single forming bar's close moves the trend reading by <1bp. But for parity with the 5M+4H paths (which both apply [:-1]), the 1H slice should match.
- **Fix:** 1-line change at line 4032 — `_c1h_closed = {k: v[:-1] for k, v in _c1h_live.items()} if _c1h_live else {}` and pass `_c1h_closed` to `get_trend`. Or simpler: `get_trend(_c1h_live.get("closes", [])[:-1])` if `_c1h_live` else "NEUTRAL"`.
