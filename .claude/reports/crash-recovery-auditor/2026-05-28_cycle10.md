## 2. NEW Findings (Cycle-10)

### M-CY10-1 — `_check_limit_fill` may leak SQLite connections on exception path  **MEDIUM**

**Severity:** MEDIUM (NEW FINDING — not in CROSS_REF)
**Location:** `/home/tradeai/TradeAI/crypto_alert.py:1532-1597`
**Classification:** NEW FINDING

**Failure mode:** `conn = _connect()` is opened at line 1540, and `conn.close()` is called at each happy/exit path (1545, 1547, 1554, 1567, 1595). However, the outer `try/except Exception` at 1532/1596 swallows any error raised between `_connect()` and one of those close points (e.g., a `cursor.execute` raising on a transient WAL lock, a `datetime.strptime` failing, an `UPDATE` blowing on schema drift). When that happens, **`conn` is never closed**, leaking a SQLite connection handle into Python GC.

**Impact in production:** SQLite uses one file descriptor per connection in WAL mode. A sustained error path during `_check_limit_fill` (called once per open signal per cycle) could leak 10s of FDs per hour. On Linux the default ulimit nofile=1024 wouldn't trip for days, but the underlying ROOT issue is that the bot's only WAL-DB cleanup discipline is `try/finally` and here the discipline is broken.

**Fix:**
```python
conn = None
try:
    conn = _connect()
    # ... existing logic ...
except Exception as e:
    print(f"[FILL] _check_limit_fill #{sig.get('id','?')}: {e}")
finally:
    if conn is not None:
        try: conn.close()
        except Exception: pass
```

5-line idiom change; eliminates the leak.

- OR rely on the systemd `Restart=always` policy for crashes (current default; covers the most common failure mode).

Documenting so it's not forgotten — not blocking.

### L-CY10-2 — `detect_smt_divergence` call sites have no try/except wrapper  **LOW**

**Severity:** LOW (defensive)
**Locations:**
- `/home/tradeai/TradeAI/crypto_alert.py:1030` (CRT path, NEW from commit `fb30114`)
- `/home/tradeai/TradeAI/crypto_alert.py:2964` (5M_SWEEP path, pre-existing)
**Classification:** NEW FINDING (introduced by the fb30114 SMT wiring fix)

**Failure mode:** Both SMT call sites pass BTC 5M candle data straight into `detect_smt_divergence`. The function looks defensive on its own (length-guard at 596 returns `_no_data`), but the downstream `min()` / `max()` / `find_ict_swings` operate on lists from `STATE["BTC"]["candles"]["5m"]` which has been observed in pathological states (None values, NaN floats during partial fetch). If any element in `ref_h`/`ref_l` is non-numeric, `min(ref_l[-lookback:])` raises `TypeError`.

The DR call at `crypto_alert.py:1045-1051` IS wrapped in try/except. The SMT call at 1030 is NOT. Asymmetric defensiveness for two equally-positioned new-wiring fixes.

**Impact in production:** A single corrupt BTC bar would propagate the exception up to `scan_h4_crt_for_token` (no inner try) → up to the main loop's outer try/except, which would bump `_consecutive_errors`. After 15 cycles the bot self-shuts-down with a CRITICAL alert. Not silent, but it converts a recoverable transient into a CRITICAL alert.

**Fix:** Mirror the DR wrapper pattern.
```python
_smt_result = {"smt_confirmed": False, "smt_type": "NONE", "reason": "no BTC reference"}
try:
    if btc_c5m and btc_c5m.get("highs") and btc_c5m.get("lows"):
        # ... existing logic
except Exception as _smt_exc:
    print(f"[CRT-SMT] {token}: detect_smt_divergence failed — {_smt_exc}")
```

Apply same pattern at line 2964 for symmetry.

### L-CY10-4 — `_check_limit_fill` opens 1 connection per open signal per cycle — connection churn  **LOW**

**Severity:** LOW (perf, not correctness)
**Location:** `/home/tradeai/TradeAI/crypto_alert.py:1540` and surrounding monitor loop
**Classification:** NEW FINDING

**Failure mode:** With N open CRT signals, `monitor_open_signals` calls `_check_limit_fill` N times per cycle. Each call opens + closes a SQLite connection. While the underlying file is shared via WAL, the open/close cycle invokes `PRAGMA journal_mode=WAL`, `PRAGMA busy_timeout=10000`, `PRAGMA foreign_keys=ON` (lines 243-245 in `_connect`) every single time. This is purely wasteful — the PRAGMAs are file-level, not connection-level.

**Impact:** At N=10 open signals and 90s cycle interval, that's ~960 superfluous connections/day. No correctness risk. Could be addressed by passing a shared `conn` from `monitor_open_signals` into `_check_limit_fill` — but that's refactor scope.

**Fix:** Optional — refactor monitor loop to reuse a single connection across all per-signal checks.

## 5. Proactive Improvement Suggestion

**Suggestion:** Add a `journalctl-detector` to the bot startup — on boot, scan the previous 5 minutes of `journalctl -u tradeai` for the pattern "exited, code=1" or "Main process exited" and fire a Telegram alert if >=3 hits found.

**Why:** The cycle-7 36-restart storm was only diagnosed in retrospect. A startup self-audit would have detected the loop and alerted within minutes instead of hours. systemd's `Restart=always` rescues the process but doesn't notify when it does so >2 times in 10 minutes.

**Impact:** HIGH — turns silent crash storms into operator-visible alerts.
**Effort:** Simple — 30 lines of code reading `subprocess.run(["journalctl", "-u", "tradeai", "--since=5 min ago", "-q"])`.
