## 3. HIGH findings

### H-CY7-A — `BOOTSTRAP_AFTER_RUN` defaults to **"1"** (on), not opt-in
- **Where:** `backtest.py:3490`
- **Cross-ref classification:** REGRESSION-from-recommendation. Master audit 2026-05-26 §D1 explicitly recommended `default OFF` as the fix for "bootstrap can silently overwrite learned weights." Code shipped it as a knob but kept default ON. Result: every `python3 backtest.py` invocation (operator manual, explorer trial that *isn't* gated, etc.) rewrites `backtest_token_weights` if it carries a `run_id`.
- **Evidence:** `_BOOTSTRAP_AFTER_RUN = os.environ.get("BOOTSTRAP_AFTER_RUN", "1") == "1"` — env-var-driven but ON by default.
- **Impact:** When the first live close fires AFTER an operator ran a 30-day ad-hoc backtest, the in-memory `_load_all()` warm-start for the 9 untouched live-row tokens reads from the just-overwritten bootstrap pool. Live `token_weights` table is unaffected (good), but the operator may unknowingly run with bootstrap weights derived from a non-canonical window.
- **Mitigation:** Set `BOOTSTRAP_AFTER_RUN=0` in `.env` for the running services; require explicit `BOOTSTRAP_AFTER_RUN=1` only inside the baseline-promotion path (`scripts/promote_baseline.py`).

### H-CY7-B — `_n_effective` is **not persisted to DB**
- **Where:** `adaptive_engine.py:347` (in-memory dict), `_persist_token()` at L868-884 writes `n_updates` but never `n_effective`
- **Cross-ref classification:** NEW FINDING (OGD-PHASEA was tracked as fixed, but persistence was not part of the original scope and is not in CROSS_REF).
- **Impact:** On bot restart, `_n_effective` for every token is silently reset to 0.0. If TON has 4 PARTIAL_TP1 closes (raw n=4, n_eff=1.6) and the bot restarts, n_eff snaps to 0.0 while raw n is recovered from DB. The per-update log "`n_eff=X.X`" diagnostic becomes lying after every restart. If a future gating refinement starts reading `_n_effective` (the docstring at L344 hints at this), it would silently misbehave.
- **Mitigation:** Add `n_effective REAL DEFAULT 0.0` column to `token_weights`; persist in `_persist_token()`. Until then, treat `n_eff` diagnostic as session-only.

## 4. MEDIUM findings

### M-CY7-A — DSR gate scales LR to 0.25× but does not communicate that to `weight_history`
- **Where:** `adaptive_engine.py:775-779` applies `_dsr_lr_scale` to `_lr`, but the value of `_dsr_lr_scale` / `_dsr_reason` is NOT persisted to the `weight_history` row.
- **Impact:** Post-hoc query "did the DSR gate fire on signal #245?" requires correlating timestamps with `bot_state.latest_cpcv_verdict` history — but `latest_cpcv_verdict` only stores the LATEST verdict, not a series. So if the verdict flips PASS→FAIL→PASS between two signal closes, the operator cannot reconstruct which signals learned at 0.25× LR.
- **Mitigation:** Add `lr_scale REAL` + `lr_gate_reason TEXT` columns to `weight_history`; populate in `_snapshot_weights()` when `trigger='signal_close'`.

### M-CY7-B — R9 active-mode freeze writes `learning_freeze_state` only **after** an alert fires (gated by 1hr dedup)
- **Where:** `_maybe_alert_freeze()` at `adaptive_engine.py:625-668`. The `learning_freeze_state` row is written inside the `now - last_alert >= OGD_FREEZE_ALERT_INTERVAL` block.
- **Impact:** First freeze event of the hour: row is written. Within the next 60 minutes, a second freeze event fires but the dedup branch is taken → `learning_freeze_state` is NOT updated even though `frozen=True` (the new triggers may be different). Dashboard reading `learning_freeze_state` sees stale data.
- **Severity:** LOW today (mode=shadow → frozen never True). Becomes MEDIUM if/when operator flips `OGD_FREEZE_MODE=active`.
- **Mitigation:** Split persistence from alerting — always write `learning_freeze_state`, only emit the print/Telegram alert under dedup.

### M-CY7-C — `_check_dsr_fail_streak` reads `first_fail_onset` correctly but does not verify it is **older than the current verdict's `updated_at`**
- **Where:** `adaptive_engine.py:570-580`
- **Edge case:** If `first_fail_onset` is a future timestamp (clock drift across services, or a manual `bot_state` edit), `age_hours` is negative and the streak check returns False — safe-fail but undetectable.
- **Mitigation:** Clamp `age_hours = max(0, age_hours)`, add a sanity print when `first_fail_onset > updated_at + 1hr`.

### M-CY7-D — Warmup ramp at n=3 produces `ramp_scale=0.0` (multiplies LR by 0)
- **Where:** `adaptive_engine.py:754`. Formula: `(n - OGD_WARMUP_FLOOR) / max(1, OGD_MIN_SAMPLES - OGD_WARMUP_FLOOR)`. At n=3, this is `(3-3)/7 = 0.0`. So the "soft warmup" at n=3 is actually a no-op step (multiplied by 0).
- **Impact:** The first effective gradient lands at n=4 (`ramp_scale=1/7≈0.143`), not n=3 as the comment claims. Continuity is preserved (no n=10 cliff), but the comment at L739-744 says "ramp from 0 → full at WARMUP_FLOOR → MIN_SAMPLES" — operator could be misled.
- **Mitigation:** Cosmetic. Either rebase the ramp at `n - OGD_WARMUP_FLOOR + 1` to give n=3 a small kick, or update the comment to explain n=3 is the *last* zero-step before the ramp begins.

### M-CY7-E — `_evaluate_freeze_predicate` runs **after** weight renormalization in the live `update()` path
- **Where:** `adaptive_engine.py:805` — called with `w_old` and the post-renorm `w`.
- **Effect:** `_check_weight_volatility_spike` measures `gradient_l1 = sum(|w_after - w_before|)` after renormalization, which subtly mixes the renorm contribution into the trigger. For comparison: the standalone `gradient_l1` written to `weight_history` (line 1372) uses the same post-renorm delta — so they agree. But this is not the *gradient* magnitude in the OGD sense; it is the *renormalized weight delta*. Threshold OGD_FREEZE_VOLATILITY_L1=0.10 must be calibrated against renorm-deltas, not raw gradients.
- **Mitigation:** Document this in the constant's comment; operator who decreases L1 threshold expecting raw-gradient semantics may oversensitize the freeze.

### M-CY7-F — Phase D.1 sandbox engine **does NOT carry the R1 DSR gate or R9 freeze**
- **Where:** `walk_forward._sandboxed_adaptive_engine()` at L478-494 clears state but inherits the module-level `OGD_DSR_GATE_MODE` and `OGD_FREEZE_MODE`. `_latest_cpcv_verdict_blob()` reads the SAME `bot_state.latest_cpcv_verdict` from the live DB. So Phase D.1 simulations during a backtest can read the **previous backtest's verdict** and modulate learning accordingly.
- **Impact:** Phase D.1 metrics (`top_decile_lift`, `wfv_ogd_wr_mean`) become non-deterministic across consecutive backtest invocations because the gate state changes between runs.
- **Mitigation:** In the sandbox, monkeypatch `_latest_cpcv_verdict_blob` to return None for clean isolation, OR explicitly set `OGD_DSR_GATE_MODE='off'` while inside `walk_forward_with_ogd()`.

### M-CY7-G — Bootstrap `extract_ict_feature_scores` is called with `signal=direction or "BUY"` — silently coerces null direction to BUY
- **Where:** `adaptive_engine.py:999`. If `backtest_signals.signal` is NULL, the bootstrap path assumes BUY, which inverts the BUY/SELL-conditional `trend_score` / `dr_score` lookup tables.
- **Impact:** Today the M14 alignment-balance warning surfaces SELL-bias, but a NULL-signal row would silently pollute BUY-bias accumulation. Frequency: low (bot writes both fields atomically). Severity: LOW.
- **Mitigation:** Skip the row when `direction not in ('BUY','SELL')`.

### M-CY7-H — Monitor timer runs daily but the report writer doesn't check the previous report's age for "stale" alerting
- **Where:** `data/monitoring/report_2026-05-26.json` is yesterday's; today's not yet generated (timer fires at 02:30 UTC = a few hours away). No alert exists for "monitor hasn't run in >36h."
- **Mitigation:** Watchdog should poll `data/monitoring/report_<today>.json` and Telegram-alert at 14:00 UTC if missing. Otherwise a silent timer failure (e.g. systemd `OnFailure=`) goes unnoticed.
