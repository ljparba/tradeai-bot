An operator debugging a "why is this backtest returning no signals for token X" would never find this. This is NEW FINDING N-2.

## 2. NEW Findings from the Fix Wave

### N-1 (MEDIUM) — CRT live scan path does not check `data_gap_bars_4h`

**File:** `crypto_alert.py:4204-4220`
**Classification:** NEW FINDING

The 5M_SWEEP path calls `generate_signal()` which checks `state.get("data_gap_bars_4h", 0) >= 1` at line 2650 and skips the signal. The CRT scan path at lines 4204-4220 has the M-NEW-5 `last_4h_fetched_at` stale-time guard but does NOT check `data_gap_bars_4h`. 

If Binance returns 4H candles with a 1-bar gap (e.g. a missing 4H candle), the live CRT detector fires with a corrupt H4 range reference. The C1 candle identification, sweep detection, and SL calculation all rely on contiguous 4H OHLCV data — a missing H4 candle produces an incorrect C1 boundary and potentially a nonsensical sweep detection.

**Why it matters today:** `data_gap_bars_4h >= 1` skips the 5M_SWEEP scan but not the CRT scan. A 4H gap event would produce asymmetric signal suppression: the slower-timeframe (CRT) signal fires while the faster-timeframe (5M_SWEEP) scan is suppressed — the exact opposite of safe behaviour.

**Fix:** Add `if STATE[token].get("data_gap_bars_4h", 0) >= 1: continue` between lines 4215 and 4216 (after the stale-time guard, before reading `_c4h`).

**Severity:** MEDIUM. Low probability event (4H candle gaps are rare on liquid pairs) but high impact when it happens.

### N-2 (LOW) — `fetch_historical` (backtest) lacks 200-OK error body guard — incomplete port of M-NEW-6

**File:** `backtest.py:334-348`
**Classification:** NEW FINDING (incomplete M-NEW-6 port)

`fetch_historical()` at `backtest.py:335` calls `batch = r.json()` without checking `isinstance(batch, dict)`. A Binance 200-OK error response like `{"code": -1121, "msg": "Invalid symbol."}` would be processed as follows:
1. `not batch` → False (non-empty dict)
2. `all_raw.extend(batch)` → extends with `["code", "msg"]` (dict keys as strings)
3. `batch[-1][0]` → `TypeError` caught at line 336
4. Log: `[FETCH ERROR] {symbol} {interval}: 'int' object is not subscriptable` (or similar)
5. Loop breaks, `all_raw` has `["code", "msg"]` strings
6. `_valid_candle(c)` at line 349 rejects all (strings fail the index check)
7. Returns `{}`

End result: safe (returns `{}`), but the diagnostic log is completely wrong. Operator would see a TypeError instead of `[BINANCE-ERR] code=-1121`. Debugging silent backtest fetch failures becomes much harder.

Add `if isinstance(batch, dict): print(f"[BINANCE-ERR] {symbol} {interval}: {batch.get('code','?')} {batch.get('msg','')}"); break` between lines 335 and 342.

**Severity:** LOW. Backtest only, not live data quality.

### N-3 (LOW) — BTC self-reference in CRT SMT detection (live path): live/backtest parity gap

**File:** `crypto_alert.py:4284-4294`
**Classification:** NEW FINDING

When `token == "BTC"`, the live CRT path at line 4284-4289 resolves `_btc_c5m_for_smt = STATE["BTC"]["candles"].get("5m", {})` — BTC's own 5M candles. This is then passed to `scan_h4_crt_for_token("BTC", ..., btc_c5m=BTC_own_candles)` which calls `detect_smt_divergence()` comparing BTC against itself. This produces meaningless SMT data (`smt_confirmed=False`, likely with reason "insufficient BTC data" or a zero-divergence result).

The backtest path correctly does `btc_c5m=None if token == "BTC" else btc_c5m_ref` at `backtest.py:3847`.

**Impact:** BTC CRT signals always get `smt_confirmed=False` in live (not from lack of SMT but from self-comparison). The +0.10 SMT tier bonus at `strategy_templates.py:531-533` is permanently dead for BTC CRT signals. Live/backtest parity gap for BTC CRT only.

**Fix:** In the live main loop: `btc_c5m=None if token == "BTC" else _btc_c5m_for_smt` at line 4294.

**Severity:** LOW. BTC CRT signals fire (no crash), but the SMT scoring is wrong for BTC only. Today BTC CRT produces valid signals but they're always scored without the SMT bonus regardless of actual SMT divergence state.

### N-4 (LOW — documentation) — `H4_CRT_C2_LOOKBACK` default mismatch between CLAUDE.md and code

**Files:** `crt_engine.py:80`, `CLAUDE.md §7`
**Classification:** NEW FINDING

`CLAUDE.md §7` states `H4_CRT_C2_LOOKBACK = _env_int("H4_CRT_C2_LOOKBACK", 6)`. The actual code at `crt_engine.py:80` is `H4_CRT_C2_LOOKBACK = _env_int("H4_CRT_C2_LOOKBACK", 10)`. The operator's `.env` sets `H4_CRT_C2_LOOKBACK=6` explicitly, so the live bot runs the intended value. But CLAUDE.md's documentation of the default is wrong — any fresh deployment without the `.env` override would use 10 bars, not 6. The `scripts/promote_baseline.py:70` fingerprint captures `os.environ.get("H4_CRT_C2_LOOKBACK", "6")` — also hardcoding the wrong default (should be `"10"` to match code, or read from `crt_engine.H4_CRT_C2_LOOKBACK`).

**Severity:** LOW / documentation. No data quality impact on the current VPS deployment (`.env` sets it explicitly). However, `promote_baseline.py` fingerprint capturing the wrong default `"6"` when the actual module default is `10` could produce incorrect key_settings fingerprints for configs that rely on the module default.
