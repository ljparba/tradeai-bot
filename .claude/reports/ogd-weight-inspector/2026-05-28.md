## 7. NEW findings (this cycle)

### MEDIUM-1 — Warmup-floor closes silently skip snapshot row (forensic gap)
- **Files:** `adaptive_engine.py:745-751`
- **Symptom:** AVAX received signal #5 close (WIN +1.96%) and signal-level OGD update fired (`weight_engine.update(snapshot=True)` called), but no `weight_history(trigger='signal_close')` row was written because the function returns at line 751 before reaching the snapshot block at 857. Operator querying `weight_history WHERE token='AVAX'` for any signal-close events gets zero rows even though the close happened.
- **Risk:** observability hole during the first 3 closes of every token's lifetime. R10 forensic panel will look like "no close ever fired" instead of "close fired but n<warmup_floor". Cumulative effect: 10 tokens × 3 warmup closes = up to 30 closes invisible to the R10 panel.
- **Suggested fix:** when `n < OGD_WARMUP_FLOOR`, still call `_snapshot_weights` with a `trigger='signal_close_warmup'` (or reuse `signal_close` with `gradient_l1=0.0` and a flag in the regime field) before the early return. 5-line patch.

### MEDIUM-2 — `last_decay_times["TON"] = 0.0` (never decayed since restart)
- **Files:** `adaptive_engine.py:1212 apply_decay_if_due`, `crypto_alert.py:3932`
- **Symptom:** `bot_state.last_decay_times` shows TON=0.0 while 9 other tokens have recent timestamps (1.8–10.5h ago). TON received 5 OGD updates today but the decay loop has never persisted a decay timestamp for it. Possible causes:
  1. apply_decay_if_due short-circuits when an OGD update happened recently (7-day post-OGD suppression guard at line ~722 may also be active).
  2. The startup `_last_decay_time[token] = 0.0` default at line 366 never gets overwritten if decay never runs for TON specifically.
- **Risk:** if TON's velocity has accumulated and decay is incorrectly suppressed indefinitely, the next big TON close could over-correct. Likely benign (post-OGD suppression is intentional), but worth verifying the 7-day guard is the actual reason rather than a code path bug.
- **Suggested action:** add a log line "decay suppressed by post-OGD guard" in apply_decay_if_due when the guard fires, so the operator can see WHY TON's timestamp isn't bumping.

### LOW-1 — POL `velocity` positive sign with `n_updates=0`
- **Files:** Bootstrap-only path; cosmetic anomaly
- **Symptom:** POL appears in `token_weights` with `velocity={0.04, 0.0206, 0.04, 0.0267, 0.0206, 0.0041}` (all positive) and `n_updates=0`. These velocities came from the bootstrap scratch engine being persisted into the live table — which CRT context §6 implies happens via `health_check_apply()` or similar fallback. Means POL's first live update will compound on stale bootstrap-era velocity.
- **Risk:** very minor — first live close will compute `MOMENTUM=0.85` × prior_velocity which is already in `[-MAX_WEIGHT_STEP=0.04, +0.04]` and clipped again. No mathematical bug, but cleanliness issue: live `token_weights` should not carry bootstrap-era velocity if `n_updates=0`.
- **Suggested fix:** during the bootstrap → live materialisation path (wherever POL got its rows populated without ever receiving a live update), zero out the `velocity` column.

### LOW-2 — XRP `fvg_quality=0.3873` in bootstrap pool (above 3× default soft-threshold)
- **Files:** Bootstrap output; observed only in `backtest_token_weights`
- **Symptom:** 3× DEFAULT_WEIGHTS["fvg_quality"] = 0.75; XRP's 0.3873 is NOT above 0.75, so the soft-threshold check at adaptive_engine.py:1138 does NOT fire. However XRP's `mss_quality=0.06` is pinned at WEIGHT_MIN (= floor saturation). This combination of "one feature dominates, four others pinned" suggests XRP's bootstrap signal mix was directional in a way that the renorm absorbed but the diagnostic missed.
- **Suggested action:** add a complementary check: when `WEIGHT_MIN` is reached on ≥3 features AND any other feature exceeds 2× default, log a "WEIGHT_DIVERGENCE" warning. Independent of the existing DEGENERATE_THRESHOLD which only looks at the single max value.

## 9. Proactive recommendations

**Suggestion 1:** Patch the warmup-floor snapshot gap (MEDIUM-1 above).
**Why:** R10 forensic panel transparency for first 3 closes per token — operator currently can't distinguish "close fired but warmup" from "close never fired."
**Impact:** MEDIUM — observability for the first 30 closes of CRT operation (cumulative).
**Effort:** Simple — 5-line patch.

**Suggestion 2:** Emit a `bootstrap_seed_live` snapshot row when bootstrap weights get copied into live `token_weights` (POL pattern).
**Why:** Closes the audit trail. Currently it's invisible whether POL/ETH/etc. got their live row from a code path or by manual SQL. Makes provenance queryable.
**Impact:** LOW — quality-of-life.
**Effort:** Simple.

**Suggestion 3:** Add per-source token_weights split (H-5 from cycle-8 carry-over) BEFORE the operator flips `ENABLE_5M_SWEEP=1`.
**Why:** Once both scanners run, the same weight vector trains on two very different feature distributions (CRT's 0.029 fvg vs 5M_SWEEP's 1.0 fvg). Schema change:
```sql
ALTER TABLE token_weights ADD COLUMN source TEXT NOT NULL DEFAULT '5M_SWEEP';
DROP INDEX IF EXISTS token_weights_pk;  /* PRIMARY KEY (token, feature) */
ALTER TABLE token_weights ADD PRIMARY KEY (token, source, feature);
```
**Impact:** HIGH — prevents cross-source contamination that would silently degrade BOTH scanners' learning.
**Effort:** Medium — schema migration + read-path updates in adaptive_engine + tracker.

**Suggestion 4:** Track effective gradient magnitude per token (sum of |gradient_l1| over last N updates) and surface it in monitoring.
**Why:** The current FLOOR-PINNED detector tells operator a feature is at the bound, but not whether the gradient is actually pushing in a useful direction. A token where all 5 closes contribute |grad|<0.005 is essentially not learning even with non-zero updates.
**Impact:** MEDIUM — surfaces "learning latency" for slow-converging tokens.
**Effort:** Medium — add per-token `cumulative_gradient_l1` column to `token_weights` or compute on-demand in monitoring.

**Suggestion 5:** Surface the `_n_effective` diagnostic (adaptive_engine.py:837) on the dashboard alongside `n_updates`.
**Why:** PARTIAL closes accumulate at `|reward| × 0.5` effective contribution. Today TON has n=5 but `n_effective` likely 3-4 due to PARTIAL_TP1 being half-weight. Operator can't see the gap.
**Impact:** LOW — diagnostic clarity.
**Effort:** Simple — already computed, just not surfaced.
