## 3. HIGH findings (degrade search quality / waste compute)

### H-1 — Error-path objective score `0.0` is higher than valid moderate-fail scores
- `autonomous_explorer.py:1038` returns `0.0` when `m.get("cpcv_mean") is None` (timeout, crashed subprocess, parse failure).
- With α=5.0, a moderate-fail trial like trial 19 (CPCV=33.4, n=226) yields `33.4 − 30.0 + 5×log(226) ≈ 30.5`. Trial 30 (CPCV=38.24, n=98): `38.24 − 30.0 + 5×log(98) ≈ 31.2`. These are *much higher* than `0.0`, so TPE correctly considers them better.
- Conversely, a low-WR FAIL: CPCV=15, n=10: `15 − 30 + 5×log(10) ≈ −3.5`. This is *worse* than `0.0`, meaning TPE will prefer the timeout/error region over the deep-fail region. With ~3% historical ERROR rate (2/37 in `backtest_explorer`), TPE may converge toward error-prone configurations.
- **Recommendation:** Change the fallback return to a clearly-bad sentinel like `-100.0` so error/timeout trials are unambiguously worse than any valid trial.
- Cite: `autonomous_explorer.py:1033-1038`.

### H-2 — `_objective` never logs config_hash on the diagnostic line
- The new diagnostic prints (lines 1030, 1035) include `cpcv_mean`, `n_bonus`, and `_n_obs` but NOT `config_hash` or `params`. Optuna logs params separately on its own info line, but having both on one line would speed forensic analysis of the 70-trial output.
- Non-blocking; cosmetic-leaning HIGH only because the operator explicitly asked about parseability.

## 4. MEDIUM findings (improvement opportunities)

### M-1 — Held-out gate (Phase C) is NOT applied to auto-promotion
- `promote_baseline.py:308-323` runs `_check_held_out_gate` only when `args.held_out_days > 0` (default 0, env `HELD_OUT_DAYS`).
- `_auto_promote()` in `autonomous_explorer.py:800-813` builds the subprocess `cmd` with no `--held-out-days` arg, and `.env.explorer` doesn't set `HELD_OUT_DAYS`.
- Net effect: this session's auto-promotion can promote a config that is overfit on the most-recent N days. With CLAUDE.md's emphasis on honest validation, this is a gap.
- Mitigation: with α=5.0 and current pin DSR=98.7%, the `_eligibility_check` `cpcv_mean ≥ 70.5` + `sharpe ≥ pin+0.02` + `dsr ≥ 95%` set is still extremely tight. The reproducibility re-run is also still required. So auto-promotion is unlikely to fire this session — but if it does, no held-out gate.
- Recommendation: add `HELD_OUT_DAYS=60` (or similar) to `.env.explorer` before next session, OR teach `_auto_promote` to pass `--held-out-days` explicitly.

### M-2 — Non-atomic JSON writes for session/pareto/promotion-log files
- `_write_session`, `_update_pareto_archive`, `_append_promotion_log` (autonomous_explorer.py:343, 691, 612) all use plain `open(..., "w")` then `json.dump`. A crash mid-write leaves a truncated file that subsequent reads can't parse.
- Impact: `--status` would print `[status] no session recorded yet`; pareto archive could be lost; promotion log corruption could mis-count `_auto_promotions_today` (returning 0 → bypass daily cap).
- Pre-existing pattern, not introduced by cycle-7. Recommend write-tmp-then-os.rename pattern eventually.

### M-3 — Stale orphan rows on subprocess-rc!=0 path
- `_run_backtest()` returns early at line 463 on `proc.returncode != 0` with no DB read or cleanup. If backtest.py crashes *after* INSERT INTO backtest_runs but before completing, the orphan row remains.
- `_objective`'s try/finally cleanup wrapper (line 995-999) will still call `_cleanup_run_row(m.get("backtest_run_id"))`, but `backtest_run_id` is never set in the error path, so `_cleanup_run_row(None)` short-circuits.
- Frequency: low (only late crashes). Net impact: minor DB bloat + potential `n_trials_for_dsr` over-count on next promotion. Recommend scoped-cleanup-by-id-range in the error branch too (mirror lines 487-501 from the success branch).

### M-4 — `_GuardState.start_sr_std` captured once at session start
- Line 544: `self.start_sr_std = _read_cross_config_std()`.
- If an auto-promotion fires mid-session, `_refresh_cross_config_std()` (line 757) updates the pool, raising `cross_config_sr_trial_std`. The guard's `start_sr_std` is unchanged, so subsequent trials compare current vs OLD baseline — likely tripping the `sr_trial_std_jump` guard immediately after the FIRST auto-promotion.
- Cycle 7 doesn't make this worse, but with the new α=5.0 alpha making promotion more likely, this latent bug is more reachable. Recommend resetting `guard.start_sr_std` inside the `if promo_result == "promoted":` block (around line 973-976).
