## NEW findings

### 🔴 H-1 — Wyckoff phase asymmetry (introduced by cycle-8 C-3 fix)

**Severity:** HIGH (HIGH at OGD attribution layer; LOW at signal-generation layer while `WYCKOFF_PHASE_FILTER=off`)
**Location:** `backtest.py:1490` (passes `c4h_win`, 12 bars) vs `crypto_alert.py:921` (passes full `c4h`, 200+ bars) — calls `crt_engine.detect_wyckoff_context` at `crt_engine.py:829`
**Defect:**
- `detect_wyckoff_context` at `crt_engine.py:856-858` requires `n >= WYCKOFF_H4_MIN_BARS = 80` else returns `"TRANSITION"`.
- `c4h_win` in backtest is `H4_CRT_C2_LOOKBACK + CRT_H4_WINDOW_BUFFER = 10 + 2 = 12` bars (`backtest.py:1359-1370`).
- → Backtest path **always** returns `"TRANSITION"` → every backtest CRT signal gets `entry_type="H4_CRT_<FVG|OB>_TRANSITION"`.
- Live path passes full cache (typically 200-500+ H4 bars, well above min_bars=80) → returns real phase labels (`ACCUMULATION`, `DISTRIBUTION`, `MARKUP`, `MARKDOWN`).
**Verification:**
```python
$ python3 -c "from crt_engine import detect_wyckoff_context; print(detect_wyckoff_context({'closes':[100]*12,'highs':[101]*12,'lows':[99]*12}))"
TRANSITION
```
SQL evidence (recent runs are PRE-fix so still show real labels — once a NEW backtest runs, all rows will be TRANSITION):
- Last 6 backtest_runs (140-145) were all before commit `78df7b2` (the C-3 fix). Run 144 (15:47 UTC) and 145 (15:58 UTC) were before C-3 at 19:13 UTC.
- Next backtest run will emit `H4_CRT_OB_TRANSITION` for every signal regardless of actual market structure.
**Impact:**
- **While `WYCKOFF_PHASE_FILTER=off` (current setting):** signal count and WR unaffected. Only the `entry_type` STRING differs.
- **For OGD attribution:** `bootstrap_from_backtest` will see TRANSITION for every backtest row → OGD's per-phase learning bucket is poisoned for CRT bootstrap. Live trades close into the real-phase buckets. Cross-source contamination.
- **For any future explorer trial with `WYCKOFF_PHASE_FILTER=loose`:** would reject 100% of CRT setups in backtest (loose mode rejects TRANSITION) → search-space corruption.
- **For any future re-enable of `strict`:** strict mode also rejects TRANSITION → BT signal count would collapse to zero while live continues firing → false belief that the filter "kills" the strategy.
**Fix (15 min):** Two options:
- (a) In `backtest.py:1490`, build a second wider sub-window specifically for Wyckoff: `c4h_win_wyckoff = {k: c4h[k][max(0, h4_end-WYCKOFF_H4_LOOKBACK):h4_end] for k in ("opens","highs","lows","closes","times")}` and pass that. Preserves the lookahead-fix intent (bounded by `h4_end`) while giving Wyckoff its 120-bar lookback.
- (b) Pass the full `c4h` but a slice ending at `h4_end`: `c4h_truncated_to_h4_end = {k: c4h[k][:h4_end] for k in ...}`. Simpler but allocates per-iteration; minor perf cost.
Either option restores live↔BT parity AND keeps the lookahead-elimination guarantee.
**Classification:** REGRESSION — the C-3 fix from cycle-8 closed a lookahead defect but introduced a parity defect. Net-positive in pure backtest validity but net-negative in live↔BT parity.

### 🟡 M-1 — CRT live `expires_at` hardcoded to 48 hours instead of `CRT_FORWARD_BARS`-derived

**Severity:** MEDIUM (asymptotic — would matter when explorer or operator changes `CRT_FORWARD_BARS`)
**Location:** `crypto_alert.py:745` — `48 if (result.get("source") == "H4_CRT") else EXPIRY_BY_REGIME.get(...)`
**Defect:** Live hardcodes `48` integer; backtest uses `CRT_FORWARD_BARS` env-overridable (576 bars = 48h at default). Explorer's CRT search space includes `CRT_FORWARD_BARS in ["288", "576", "864"]` (autonomous_explorer.py:511) — at 288 (24h) or 864 (72h), backtest expiry window changes but live expiry stays at 48h.
**Fix (2 min):** Replace `48` with `int(CRT_FORWARD_BARS * 5 / 60)` (5M bars × 5min / 60min = hours) where `CRT_FORWARD_BARS` is imported from `crt_engine` at top of `crypto_alert.py`.
**Classification:** NEW FINDING — surfaced by audit, no prior cross-ref entry.

### 🟡 M-2 — Live passes `precompute_tf` not invoked on `c1h_live`

**Severity:** LOW (semantically equivalent given EMA formulas are identical, but mathematically different code paths)
**Location:** `crypto_alert.py:4081` `_crt_trend_1h = get_trend(_c1h_live.get("closes", []))` vs `backtest.py:1458-1459` `_ind1h = precompute_tf(c1h); _trend_1h = _lookup_trend(_ind1h, c5m["times"][entry_bar])`
**Defect:** Live calls `indicators.get_trend()` (uses `indicators.ema()`). Backtest calls `_trend_from_ema()` on the pre-computed EMA series from `_ema_series()`. Both EMA formulas are mathematically identical (SMA-seed + α-smoothing with same α = 2/(period+1)), but the two code paths use different implementations. Any future "optimization" to one (e.g. Wilder smoothing in `_ema_series` only) would silently diverge.
**Fix:** Long-term — consolidate to single shared `ict_engine`-level helper. Short-term: add a unit test `tests/test_live_bt_trend_parity.py` that asserts `get_trend(closes) == _trend_from_ema(closes[-1], _ema_series(closes,50)[-1], _ema_series(closes,200)[-1])` on a synthetic 300-bar series.
**Classification:** NEW FINDING.
