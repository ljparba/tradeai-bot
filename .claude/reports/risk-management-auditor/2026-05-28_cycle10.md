**The flaw:** The 5M_SWEEP path calls `evaluate_template_status()` (line 3238) which enforces:
1. INSUFFICIENT_SAMPLE gate (requires 50 closed trades per template before LIVE)

3. DAILY_CAP_REACHED gate (respects TIER_DAILY_LIVE_CAPS per template)

This field is `1` for CRT_A_FVG_ALIGNED and CRT_B_OB_HIGH_MSS because those templates have `live_allowed=True` hardcoded in the registry. `evaluate_template_status()` is **never called** for CRT signals.

**Worst-case scenario in LIVE mode:**
- Operator flips `EXECUTION_MODE=LIVE` with 0 closed CRT trades
- Bot generates CRT Tier A signal (FVG + MSS≥MEDIUM, extremely common)
- `template_live_allowed=1` → LIVE block condition at line 4386 evaluates False → signal reaches Telegram

- Daily cap `TIER_DAILY_LIVE_CAPS` has no entry for `CRT_A_FVG_ALIGNED` — even if `evaluate_template_status` were called, it would read `TIER_DAILY_LIVE_CAPS.get("CRT_A_FVG_ALIGNED", 0) == 0` and return PAPER_ONLY — which is the WRONG behavior (Tier A is live-allowed)

**Secondary gap:** `TIER_DAILY_LIVE_CAPS` in `config.py:257-262` has no CRT template entries. If `evaluate_template_status` were ever wired for CRT, the `cap = TIER_DAILY_LIVE_CAPS.get(template_id, 0)` at line 1281 would return 0 for all CRT templates, treating them all as PAPER_ONLY — contradicting the `live_allowed=1` registry definition.

**Mitigating factors today:** PAPER mode is active. LIVE requires manual operator flip + `LIVE_MODE_CONFIRMED=YES` + `YOUR_CAPITAL` set + CRT honest-metric clearance gates (currently FAIL at WR≈48%/DSR≈25%). The operator's discipline is the only protection for this gap right now.

1. Add CRT template IDs to `TIER_DAILY_LIVE_CAPS` in `config.py` (e.g., `"CRT_A_FVG_ALIGNED": 3, "CRT_B_OB_HIGH_MSS": 2, "CRT_B_FVG_RELAXED": 2, "CRT_C_OB_DEFAULT": 0`)

**Effort:** Simple (3 lines in scan_h4_crt_for_token)

**Suggestion 2 — Add BLOCK_RANGING_TEMPLATES entry for CRT_C_OB_DEFAULT**
**Why:** `BLOCK_RANGING_TEMPLATES = {"TIER_B", "NONE"}` in config.py doesn't include any CRT template IDs. In RANGING regime, CRT_C_OB_DEFAULT (catch-all OB) should be blocked in LIVE just like TIER_B and NONE are. **Impact:** LOW (CRT_C is already paper-only)
**Effort:** Simple (add CRT_C_OB_DEFAULT to BLOCK_RANGING_TEMPLATES)

**Suggestion 3 — Per-session risk cap for CRT**
**Why:** CRT emits ~15-17 signals/month vs 5M_SWEEP's ~2-3. With 10 tokens, multiple CRT signals can fire in a single London or NY session. The portfolio risk gate (3%) limits total open exposure, but there's no per-session cap to prevent entering 3 correlated positions in the same 4-hour killzone window (London: BTC+ETH+BNB all showing H4 CRT BUY simultaneously during risk-on open).
**Impact:** MEDIUM (correlation risk is structurally handled by the CORRELATED guard, but the session-clustering risk is different)
**Effort:** Medium (new session-aware counter in portfolio_layer.check())

**Suggestion 4 — CRT-specific CIRCUIT_BREAKER threshold**
**Why:** The 5M_SWEEP path runs CIRCUIT_BREAKER_MIN_WR=55% which is appropriate for its 82.8% WR baseline. CRT's baseline WR is 54-60% — a 55% circuit breaker would pause CRT on normal statistical variation. Consider `CRT_CIRCUIT_BREAKER_MIN_WR=0.45` to reflect CRT's lower expected WR. Currently the circuit breaker is only meaningfully applied for 5M_SWEEP (CRT bypasses it via RISK-GAP-NEW-1 above), so this is moot until Action 1 is done.
**Impact:** MEDIUM
**Effort:** Simple (add env-overridable config.CRT_CIRCUIT_BREAKER_MIN_WR, use in evaluate_template_status for CRT template IDs)
