## Section A — Telegram send infrastructure

**Files:** `/home/tradeai/TradeAI/crypto_alert.py:3018` (`send_telegram`), `/home/tradeai/TradeAI/scripts/watchdog.py:51` (`_send_telegram`), `/home/tradeai/TradeAI/scripts/autonomous_explorer.py:347` (`_telegram`).

### Findings

- **Env-sourced secrets**, never hardcoded:
  - `crypto_alert.py:122`: `TELEGRAM_TOKEN = os.environ.get("TELEGRAM_TOKEN", "")`
  - `CHAT_ID` is loaded the same way via `secrets_loader.load_env`.
  - `.env` confirmed: `TELEGRAM_TOKEN=<SET>` `CHAT_ID=<SET>` (values not displayed).
- **Retry discipline (`send_telegram`)**: 3 attempts, linear back-off `5s → 10s → 15s` (`crypto_alert.py:3018-3060`). HTTPS timeout 10s per attempt.
- **Parse-mode failover**: on Telegram 400 *"can't parse entities"*, the function strips HTML tags via `re.sub(r"<[^>]+>", "", message)` and retries as plain text (`crypto_alert.py:3040-3044`). Good — defends against unescaped `<` or `&` in dynamic content.
- **All dynamic interpolation is wrapped in `_h()` = `html.escape`** (`crypto_alert.py:28-36`). `send_signal_msg` consistently uses `_h(...)` around tokens, sig_id, status strings (verified lines 3133-3215). Float values use direct format-strings (`:.5f`, `:.4f`) which are safe.
- **Endpoints used:** **`sendMessage` only.** No `sendPhoto`/`sendDocument`/`sendMediaGroup`. QuantStats tearsheets are not pushed via Telegram (per CLAUDE.md §6 they live in the dashboard which is hidden until LIVE).
- **Failure mode is graceful:** total failure logs `[TG FAILED]` + truncated message preview to stdout; caller gets `False`. **Signals are saved to DB BEFORE the Telegram call**, so Telegram failure never loses a signal:
  - 5M_SWEEP path (`crypto_alert.py:3674`): `sig_id=save_signal(...)` then `send_signal_msg(...)`.
  - CRT path (`crypto_alert.py:3711-3729`): same order — `_crt_sig_id = save_signal(...)` then `send_signal_msg(...)`.
- **Three parallel Telegram client implementations:**
  - `crypto_alert.send_telegram` (the main one — 3-retry + HTML→plain fallback).
  - `scripts/watchdog._send_telegram` (single-shot + HTML→plain fallback).
  - `scripts/autonomous_explorer._telegram` (single-shot + HTML→plain fallback).
  All three read the SAME `TELEGRAM_TOKEN` and `CHAT_ID` env vars → same chat. No risk of message-to-wrong-channel.

### Verdict for A
**🟢 LOW issues only.**

- 🟢 LOW A-1: `send_telegram` does not honor Telegram's `Retry-After` header on 429s (treats all HTTP errors the same — backoff `5s × attempt`). Acceptable because total alert volume is low (~25-30/day in steady state — see §G).
- 🟢 LOW A-2: Watchdog and explorer Telegram clients duplicate logic that lives in `crypto_alert.send_telegram`. Drift risk if retry policy or escape strategy evolves.

### Findings

- **🔴 CRITICAL B-0 — KeyError on `plan['net_tp1_pct']`.**
  - CRT plan dict (`crypto_alert.py:938-950`) contains 11 keys: `sl, tp1, tp2, tp3, sl_pct, tp1_pct, tp2_pct, tp3_pct, rr1, rr2, rr3`.
  - Renderer (`crypto_alert.py:3188-3195`) uses bracket-access (NOT `.get`) on three keys not present in the CRT plan:
    ```python
    f"Net TP1 {plan['net_tp1_pct']:+.2f}%  -  "
    f"BEW {plan['breakeven_wr']:.0%}  -  "
    f"Net R:R {plan['net_rr1']}\n"
    ```
  - Note: `net_rr1` and `breakeven_wr` ARE computed in `crt_engine.compute_crt_trade_economics` (`crt_engine.py:608-636`) — they live in the `econ` dict — but the CRT path's `plan = {...}` only copies the `gross_*` and `rr1/rr2/rr3` values, not the `net_*` ones (`crypto_alert.py:943-947`). And `net_tp1_pct` itself is NOT computed by the CRT economics helper (it only computes `net_tp1` raw, not the percentage).
  - The 5M_SWEEP path's plan dict (built in `crypto_alert.py:2278-2289`) does include these three keys → 5M_SWEEP signals render fine.
  - Outcome: when the first CRT signal fires, `send_signal_msg` raises `KeyError: 'net_tp1_pct'`. The exception bubbles out of the per-token loop into the outer cycle exception handler (`crypto_alert.py:3771-3783`), which sends:
    ```
    <b>Bot ERROR  -  cycle failure #1</b>

    <pre>'net_tp1_pct'</pre>
    Bot is retrying. Investigate if this persists:
    <code>journalctl -u tradeai -n 50</code>
    ```
  - The signal is saved to DB and `consumed_h4_crt` is updated *before* `send_signal_msg` runs, so the same setup will NOT re-fire. **Net effect: every CRT signal is invisible to Telegram, and the operator gets a confusing "cycle failure" alert instead.**
  - Fix (preferred): in the CRT plan dict at `crypto_alert.py:938-950`, add:
    ```python
    "net_tp1_pct":  round(econ["net_tp1"], 2),
    "net_rr1":      econ["net_rr1"],
    "breakeven_wr": econ["breakeven_wr"],
    ```
  - Fix (alt, defensive): change `crypto_alert.py:3192-3194` to use `.get` with sensible fallbacks (`plan.get('net_tp1_pct', plan['tp1_pct'])` etc.). This also hardens against future plan-shape drift.

- **🟠 HIGH B-1 — HTF line is silently wrong for CRT.** `crypto_alert.py:3093-3094`:
  ```python
  trend_1h = result.get("ict_trend_1h", "NEUTRAL")
  bias_4h  = result.get("ict_bias_4h", "NEUTRAL")
  ```
  CRT does not set those keys — it sets `trend_1h` and `mtf_bias`/`trend_4h` (`crypto_alert.py:957-961`). The Telegram message will display `HTF  4H NEUTRAL / 1H NEUTRAL` even when CRT internally confirmed BULL/BULL. **Wrong info is worse than missing info.** Especially harmful because `LIVE_BIAS_4H_GATE=strict` — operator is relying on the 4H bias to interpret directional alignment.

- **🟠 HIGH B-2 — No scanner-source distinction.** The message header is `<TOKEN> <BUY/SELL> signal #<ID>`. There is no emoji, no `[CRT]` tag, no source label anywhere in the rendered message. When `ENABLE_5M_SWEEP=1` is re-enabled later, the operator will need to SQL-inspect `signals.source` to tell signals apart. Today (with `ENABLE_5M_SWEEP=0`) all signals are CRT, but the moment both scanners run, this becomes a daily-operations gap. The CRT path already saves `source='H4_CRT'` (`crypto_alert.py:995`) and uses `sr_type='SSL_CRT'/'BSL_CRT'` (`crypto_alert.py:977`) — both already in the DB, both unused by the renderer.

- **🟠 HIGH B-3 — Wyckoff phase is not visually prominent.** The Wyckoff tag is hidden in two non-obvious places:
  - The `Reaction` line of the ICT-setup `<pre>` block, which reads `Reaction H4_CRT_FVG_MARKUP`.
  - The last bullet of the `Why this signal:` list, which reads `- wyckoff=MARKUP`.
  Neither is a dedicated `Wyckoff Phase: MARKUP` line. Per the operator's note that this is the new top-of-mind variable for manual trade management, it deserves a top-row callout near the title. (The operator runs `WYCKOFF_PHASE_FILTER=off`, so the phase is informational, not blocking — but informational signals should still be obvious.)

- **🟡 MEDIUM B-4 — FVG range shows `0.00000 - 0.00000`.** Because `result["ict_fvg"]` carries only `{"quality": ...}` (`crypto_alert.py:981`), `fvg_top`/`fvg_bot` default to 0.0 and `fvg_size_pct = 0`. Operator sees `FVG  0.00000 - 0.00000  (0.00%, HIGH)`. Either populate top/bottom from the OB/FVG zone returned by `crt_engine._check_confluence`, or branch the renderer to skip the line when `result["source"] == "H4_CRT"`.

- **🟡 MEDIUM B-5 — `Sweep ? @ 0.00000`.** `result["ict_sweep"]` is unset. CRT's analog is "C1 swept C0 high/low" — the sweep-level is `c1_high` for BSL_CRT (SELL) and `c1_low` for SSL_CRT (BUY). Should show e.g. `Sweep BSL_CRT @ 65612.30`.

- **🟡 MEDIUM B-6 — `Size $0 / Risk 0.0% ($0.00) / Fees ~$0.00`.** `sizing` block not populated by CRT. In PAPER mode this is cosmetic, but the all-zero line reads like a "broken UI" symptom. Either compute sizing same as 5M_SWEEP via `_get_position_sizing(...)`, or skip the entire block when `sizing == {}`.

- **🟡 MEDIUM B-7 — EV line renders `N/A (n=None, OBSERVE)`.** `result["ev_sample_n"]` is set to `None` (`crypto_alert.py:986`); `f"n={None}"` produces the literal string `None`. Trivial fix: set `ev_sample_n=0` for CRT, or branch the renderer to skip the EV line when `ev_sample_n is None`.

- **🟡 MEDIUM B-8 — `CRT_TP1_MODE` not surfaced.** With `CRT_TP1_MODE=min_1r`, TP1 may equal C1-opposite OR 1R, depending on which is larger. Operator sees `TP1 65648.70 +0.33% R:R 1.0 close 40%` with no tooltip about which case fired. The renderer already reads `tp1_lbl = result.get("tp1_target_type", "")` (`crypto_alert.py:3102`) but never displays it — surface the variable and have the CRT path set it to e.g. `"min_1r→1R_fixed"` or `"min_1r→c1_high"`.

- **🟡 MEDIUM B-9 — `regime_emoji` computed but never inserted into the message** (`crypto_alert.py:3073-3074`). For CRT, regime is hard-coded `"UNKNOWN"` → `❓`. Either drop the dead variable or wire it in.

- **🟡 MEDIUM B-10 — Template tag confusion.** Header reads `<b>Conf 8/10</b>   NONE UNKNOWN_TEMPLATE (PAPER)`. The literal string `PAPER` is computed from `_tmpl_live = 0` (`crypto_alert.py:3128`: `"LIVE-OK" if _tmpl_live else "PAPER"`). For CRT signals this is hard-coded `0`. So the tag is `PAPER` *regardless of EXECUTION_MODE*. The italic line `Template blocked: crt_v1_no_template` also fires. For a PAPER-mode CRT-only operator, this is fine but confusing — looks like the bot saying "this is a paper trade because template blocked LIVE" when actually CRT just doesn't have templates yet.

- **🟢 LOW B-11 — `dom_arrow` and `bar` (confidence-bar string) are computed but never inserted into the message** (`crypto_alert.py:3082, 3064`). Dead code.

## Section F — Watchdog Telegram alerts

**File:** `scripts/watchdog.py`. Service: `tradeai-watchdog.service`. Independent process — survives `kill -9` of the main bot.

### Findings

- **Same token + chat_id** — `watchdog.py:54-55` reads `os.environ.get("TELEGRAM_TOKEN")` and `CHAT_ID`. Single channel. ✓
- **Alert conditions** (`watchdog.py:137-213`):
  - Heartbeat file missing → `<b>BOT NOT RUNNING</b>`
  - Heartbeat file stale > 600s (default) → `<b>BOT FROZEN  -  no heartbeat for N min</b>`
  - Heartbeat resumes after STALE → `<b>BOT RECOVERED</b>`
